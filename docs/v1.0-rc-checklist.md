# v1.0 RC Checklist

This checklist governs each release candidate for v1.0, including `v1.0.0-rc.1` and any subsequent RC.

Use it alongside [release-checklist.md](release-checklist.md) for the broader pre-release gate set.

## Pre-RC Validation Checklist

Complete every item before cutting or re-issuing an RC.

### Repository Hygiene

- [ ] Working tree is clean except intentionally staged release changes.
- [ ] Unrelated feature work is excluded from the RC branch.
- [ ] Version references across docs, dashboard, and changelog are internally consistent.
- [ ] No stale validation numbers remain in README, dashboard, roadmap, or release notes.

### Validation Gates

- [ ] `npm run validate` passes.
- [ ] `npm run validate:all` passes.
- [ ] `npm run eval:report` passes all required safety checks.
- [ ] `npm run smoke-test:cli` passes.
- [ ] `npm run test:e2e` passes.
- [ ] `node scripts/smoke-test-adapters.mjs` passes for all adapters.
- [ ] `node scripts/validate-secrets.mjs` passes.

### Schema and Reference Gates

- [ ] `npm run validate:schemas` passes if registry contract or schema files changed.
- [ ] `npm run validate:references` passes if reference intelligence files changed.
- [ ] `npm run validate:traceability` passes if commands, skills, templates, or docs links changed.

### Stability

- [ ] No unreviewed breaking changes to the core workflow contract.
- [ ] No breaking changes to Tier 1 adapter surfaces without migration notes.
- [ ] No unresolved RC feedback classified as a blocker.
- [ ] No unlicensed third-party content included.

## Release Notes Requirements

The RC release notes must include:

- **RC label:** the tag must clearly indicate `v1.0.0-rc.N`.
- **What changed since v0.4.0:** top-level summary of stabilization work.
- **What is stable in v1.0:** the core contract, validation gates, adapter support tiers, and compatibility policy.
- **Known issues:** any documented RC limitations or deferred follow-ups.
- **How to upgrade from v0.4.0:** migration or adoption notes if user workflow changes.
- **What to test:** focus areas for RC feedback, such as docs clarity, adapter install steps, CLI commands, and validation pass behavior.
- **How to give feedback:** preferred issue template or channel.

## Documentation Completeness Checks

Before any RC, confirm:

- [ ] `docs/v1.0-release-plan.md` matches the actual RC scope.
- [ ] `docs/v1.0-rc-checklist.md` is being followed and is current.
- [ ] `docs/support-matrix.md` matches adapter support tiers and runtime expectations.
- [ ] `docs/compatibility-support-policy.md` matches the support tiers used in docs and roadmap.
- [ ] `docs/release-checklist.md` covers every validation gate expected for the RC.
- [ ] `docs/ROADMAP-STATUS.md` reflects current v1.0 status.
- [ ] `docs/DASHBOARD.md` reflects current validation and adapter state.
- [ ] `CHANGELOG.md` has an accurate `[Unreleased]` section before tagging.
- [ ] Adapter READMEs and `adapters/compatibility-matrix.md` are current.
- [ ] README and README.vi reflect the current release posture and status line.

## Post-Merge Verification Steps

After the RC merge lands:

1. Confirm the branch is clean.
2. Confirm `npm run validate:all` still passes on main or the release branch.
3. Confirm the release notes file and changelog entries survived the merge correctly.
4. Confirm dashboard and roadmap are not stale.
5. Confirm the tag was created from the expected commit.
6. Confirm GitHub Release content matches the release notes draft.
7. Capture one verification summary with evidence snippets or links.
