## 2. Pain Points v2.16.0 ACTUALLY Solves (verified, not promised)

### 2.1 Context discipline (real)
- `skills/core/code-context-pack/SKILL.md` — forces inspection of "nearby implementations, tests, conventions, and constraints" before any edit. This is a direct counter to "agent invents from training data." Verified content, 30+ lines.
- `skills/core/context-rich-implementation/SKILL.md` — index entry promises "an executor can finish a task in one pass."
- `skills/core/context-policy/SKILL.md` — index promises policy-based context-window control. No "magic" context window, but real discipline.

### 2.2 Spec/plan/verify loop (real, end-to-end)
The loop `Intent → Spec → Plan → Implement → Test → Review → Memory → Merge` is not just marketing — every step has both a `commands/vibe-*.md` prompt and a `skills/core/*/SKILL.md` skill. The `docs/workflows/core-vs-optional-runtime.md` file draws the line clearly: the **core portable layer** (`skills/`, `commands/`, `templates/`, root guidance) is the product, and the runtime is optional. A developer who can't install anything still gets value.

### 2.3 Security: Defense in Depth, now wired (verified)
This is the v2.16.0 marquee. Three layers, all present on disk:
- **Layer 1 DETECT:** `security/defense/injection-counters.mjs` + `security/defense/trust-scorer.mjs` (new in v2.16.0, ADR 0004).
- **Layer 2 CONTAIN:** `security/redact/redactor.mjs` (3 modes: postTool/postSession/postPublish).
- **Layer 3 RECOVER:** `tests/security/regression.mjs`.
- RTL coverage documented as 100% (was 97.37%); `security/defense/patterns/canary-corpus.v1.json` exists. The v2.16.0 wave-A detail explains the actual gap (U+202E attacks where invisible chars reverse "delete everything").
- This directly addresses the **#1 pain point** vibe coders worry about: pasting third-party content into the agent and getting pwned.

### 2.4 Anti-rubber-stamp review (real)
`skills/core/adversarial-code-review/SKILL.md` is explicitly *"not a polite rubber-stamp review: approval must be earned by evidence."* `skills/core/review-before-merge/` and `skills/core/receiving-code-review/` close the loop on both sides.

### 2.5 TDD enforcement (real, but thin)
`commands/vibe-tdd.md` and `skills/core/test-driven-development/SKILL.md` are real and small. They exist. They are short enough to actually paste.

### 2.6 Spec template + checkpoint gate (real)
`templates/spec-template.md` (43 lines, real structure) + `skills/core/checkpoint-validation/SKILL.md` + `templates/checkpoint-template.md` mean there is an explicit go/no-go gate between phases. `skills/core/spec-first-development/SKILL.md` includes a non-obvious gem: a *scenario pattern taxonomy* (happy / error / edge / performance / security) and a scenario-validation checklist — this is one of the few places in the framework that **explicitly forces the developer to think about the security boundary scenario** before code.

### 2.7 Hooks pack for Claude Code (real, narrow)
`skills/core/claude-code-hooks-pack/SKILL.md` (72 lines) gives a recipe for `.claude/settings.json` hooks (`PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`, `SessionStart`, `SessionEnd`) with exit-code semantics (0 = allow, 2 = block). Genuinely useful; fills the gap between 136 planning skills and day-to-day safety.

### 2.8 Discoverability (real, finally)
New in v2.16.0: `commands/vibe-skill-search.md` for FTS5/regex across all skill content, and `commands/vibe-deps-graph.md` for visualizing the skill dependency graph. Both address the *real* complaint that 88 (now 152) skills are not navigable.

### 2.9 Quality elevation discipline (real, but separate layer)
`skills/core/quality-shield/SKILL.md` (index entry) and the related `docs/quality-shield.md` / `docs/quality-engine-guide.md` / `docs/quality-telemetry-guide.md` form a stack: contract → context pack → smallest safe diff → self-review → scorecard → telemetry. Real, but it lives in *its own* layer above the default loop — easy to never discover.

## 3. Pain Points STILL UNSOLVED (verified gaps)

### 🔴 CRITICAL

1. **No automatic template binding.** When a developer types `/vibe-spec` or pastes the `vibe-spec` command, the system does *not* automatically load `templates/spec-template.md`. The command file says "Save or present the spec using the repository's spec conventions" — but a vibe coder on day 30 will not remember to open the template. There is no template-picker skill. **Result:** specs are freeform, inconsistent, un-reviewable.

2. **The 88 (actually 152) skills are still un-navigable without search.** `vibe-skill-search` and `vibe-deps-graph` were *just* added in v2.16.0 and almost no in-doc cross-links point to them. A new developer staring at `skills/core/INDEX.md` still has to scroll through 8 lifecycle groups to find anything. **There is no decision-tree tool, no "I want to add OAuth" → "use these 4 skills" guidance.** The decision tree doc exists (`docs/workflows/plan-skill-decision-tree.md` per the brainstorming skill pointer) but is referenced only from inside one skill.

3. **Coverage and trust are still in tension.** The v2.16.0 master plan *itself* admits the framework has ~4.6% test coverage and that v2.16.0 raised it to ~15%. The framework asking vibe coders to trust its quality-discipline recommendations when *the framework itself is undertested* is a real credibility gap. (`docs/reports/council/v2.16.0-master-plan.md` — "Engineering B+ (8.0/10) — Governance mature, behavior under-verified (4.6% test coverage).")

### 🟠 MEDIUM

4. **No "from a one-line ask to a verified PR" end-to-end demo.** `examples/react-nextjs-booking-workflow/` exists but it is a *complete example*, not an *interactive tutorial*. `docs/TUTORIAL.md` is referenced but I didn't see evidence it walks through an actual real-world feature with screenshots / actual prompts / actual outputs. A vibe coder's first 30 minutes are the highest-friction moment; this is unsolved.

5. **The default loop skips Quality Shield by default.** The 8-step `Intent → Spec → Plan → Implement → Test → Review → Memory → Merge` loop in `README.md:114-126` does not include "Contract" or "Scorecard." Quality Shield is opt-in (`docs/quality-shield.md`) but the README never says "use Quality Shield by default for non-trivial changes." New users miss the strongest defense the framework offers.

6. **Spec-first development skill itself is too long.** `skills/core/spec-first-development/SKILL.md` is 110 lines. Pasting 110 lines of skill *plus* a 33-line command *plus* a 43-line template every time a developer wants to spec a 1-hour change is too much friction. There is no "lite" version, no adaptive default.

7. **`vibe init` has multiple flags that are not documented in QUICKSTART.** `commands/vibe-init.md` is a generic orient-the-session prompt, but the QUICKSTART shows `vibe init claude-code` / `cursor` / `codex` / `gemini` (one-arg) AND the CLI section shows `--tool`, `--scope`, `--current-terminal`, `--project`, `--dry-run` flags. None of the flag semantics are in QUICKSTART. New users discover flags by trial.

8. **No mutation testing, no property-based test by default.** `docs/property-based-testing.md` and `scripts/property-test-runner.mjs` exist, but neither appears in the default workflow loop. A vibe coder's agent writes tests that *pass* but may not *test* the right thing. The framework has the tools but does not make them the default.

9. **Cursor / Gemini / Codex paths are clearly second-class.** The CLAUDE.md path is the recommended one. Codex reads `AGENTS.md` (`AGENTS.md:43-45`), Gemini reads `GEMINI.md` (manually cp'd). For a developer who lives in Cursor (a large audience), there is no plugin, no per-repo bootstrap command, no `vibe init cursor` shortcut shown in QUICKSTART that actually copies anything — the QUICKSTART says "paste the contents of CLAUDE.md into project rules." That is a real UX gap.

### 🟢 NICE-TO-HAVE

10. **No way to compare versions of a spec/plan over time.** Specs are markdown files; git diffs work, but there is no `vibe spec diff spec-v1 spec-v2` command.
11. **No per-project "memory" file convention surfaced in the workflow.** `skills/core/lessons-learned-db/` and `docs/memory-conventions.md` exist, but the README's default loop says "Memory" with no pointer to the convention. New users have no idea *where* to write durable lessons.
12. **No `/vibe-*` plugin installation verification step.** QUICKSTART tells you to run `/plugin list` after install but does not show the expected output. If the install silently fails, a vibe coder has no immediate signal.

## 5. Top 5 Recommendations for v2.17.0

1. **Ship a one-command end-to-end demo.** `vibe demo invoicer-csv` (or similar) that takes a one-line goal, runs spec → plan → implement → review → verify on a known starter repo, and shows the user every output. Today's `examples/react-nextjs-booking-workflow/` is a static read; an *interactive, runnable* demo is what closes the day-1 activation gap.

2. **Auto-bind templates to commands.** Make `vibe-spec` automatically inject `templates/spec-template.md`, `vibe-plan` inject `templates/plan-template.md`, `vibe-tdd` inject a minimal red-green checklist. One-line `--dry-run` preview to learn what each step produces.

3. **Default-on Quality Shield for non-trivial work.** Change `README.md:114-126` so the 8-step loop inserts **Contract → Context pack → Smallest safe diff → Self-review → Scorecard** as *required* phases for any change spanning >1 file or touching behavior. Today it lives in a separate doc that almost nobody finds.

4. **Fix the "what skill do I use?" problem with a decision tree, not an index.** Build `vibe doctor --goal "add OAuth"` that reads the goal, queries `registry/skills.json` + `commands/manifest.json`, and prints the exact skill/command/template chain with clickable paths. The `skills/core/skill-content-search` and `vibe-deps-graph` commands exist but require the user to know they want them.

5. **Close the credibility gap: ship v2.17.0 with ≥40% framework test coverage and make `npm run validate:all` part of the user-facing quickstart.** The v2.16.0 master plan itself flags the framework's own 4.6%→15% coverage as a critical issue. A vibe coder who runs `npm run validate:all` once and sees real tests passing for real framework code will trust the discipline; today's gating is structural-only and easy to dismiss as bureaucratic.

## Audit Verdict

**v2.16.0 is real.** Every command and skill I opened has substantive content. The spec → plan → verify loop is end-to-end and works in markdown alone. Security wiring (Trust Scoring, RTL 100%, redactor) is the most material improvement and is genuinely differentiated from competitor frameworks.

**v2.16.0 is also still under-baked at the seams.** Template-to-command binding is missing. The default loop bypasses the strongest layers (Quality Shield, adversarial review). Skill discovery requires a search tool the user doesn't know about. The framework itself ships at ~15% test coverage. And for non-Claude-Code users (Cursor, Gemini), the path is still "manually paste CLAUDE.md into rules."

The ceiling is high. The floor — *what a developer experiences in their first hour* — has not been raised as much as the marketing implies.
