# Panel B — Platform/Runtime Engineer Audit: v2.17.0 Runtime Layer

**Date:** 2026-06-22
**Version:** 2.17.0 (Expert Council Trim release)
**Scope:** Runtime layer production-readiness — MCP server, autopilot stack, install path, validators, CLI tools, security wiring
**Method:** Fresh-tmp-dir testing, source audit, npm dry-run, smoke-test execution
**Head SHA:** (dirty working tree — deps installed, .vibe/runtime exists)

---

## Executive Summary

**Rating: NEEDS WORK — 3 critical gaps, 4 moderate gaps, 2 advisories.**

The v2.17.0 runtime layer ships with a functional MCP server (starts, serves 15 tools over stdio), clean dependency graph (0 vulns), and a well-designed approval-gate middleware with 15/15 passing unit tests. However, three critical issues make the runtime **not production-ready**:

1. **`--help`/`--tools` expose only 11 of 15 tools** — the autopilot tools are excluded from the CLI introspection surface, violating the "15 tools advertised" contract.
2. **`tool-contract.mjs` blocks 9 of 15 tools at runtime** — the `defaultContracts.mcp` allowlist only covers the 6 core tools; calling `vibe.*` or `autopilot.*` tools via MCP will throw `"Tool not allowed for adapter mcp"`.
3. **`.vibe/` directory leaks into git** — autopilot session state (.json files, audit.log) written to `.vibe/runtime/autopilot/` is NOT covered by `.gitignore` (only `.omc/` is), creating a security/privacy exposure.

## 1. MCP Server Production Test

### 1.1 Server Startup

Test on fresh temp directory:

```
$ cd /tmp/vibe-mcp-test && timeout 5 node /path/to/scripts/runtime-mcp.mjs
vibe-coding-os-runtime v2.17.0 listening on stdio (15 tools).
```

**✅ PASS** — Server starts cleanly on fresh checkout. SDK is present (`@modelcontextprotocol/sdk 1.29.0`). The `loadSdk()` lazy-import pattern in `runtime/mcp/server.mjs:137-156` gracefully handles missing SDK with a helpful install message rather than crashing.

### 1.2 Tool Surface Verification — CRITICAL FAIL

**CLAIM:** 15 tools (6 runtime + 5 vibe commands + 4 autopilot).
**REALITY:** Only 11 tools appear in `--help` and `--tools` output.

```
$ node scripts/runtime-mcp.mjs --tools | python3 -c "import sys,json; print(len(json.load(sys.stdin)))"
11
```

**Root cause:** The `printHelp()` function and `--tools` handler in `scripts/runtime-mcp.mjs:24-56` only call `buildTools()` and `buildCommandTools()` — they **omit `buildAutopilotTools()` entirely**.

```
scripts/runtime-mcp.mjs:26-28
  const tools = [
    ...buildTools(createStore(process.cwd())),
    ...buildCommandTools(process.cwd()),
    // buildAutopilotTools(process.cwd())  ← MISSING
  ];
```

The actual server start path (line 59) correctly includes all three tool sets via `server.mjs:169-176`:

```javascript
const tools = [
    ...buildTools(store),           // 6 tools
    ...buildCommandTools(root),     // 5 tools
    ...buildAutopilotTools(root),   // 4 tools
].map(/* ... */);
```

So the MCP server does register 15 tools at runtime, but the CLI introspection (`--help`, `--tools`) is wrong. Any client relying on these flags to discover the tool surface will miss 4 autopilot tools.

### 1.3 Tool Contract Allowlist — CRITICAL FAIL

**File:** `runtime/core/tool-contract.mjs:8-15`

```javascript
export const defaultContracts = {
  native: [],
  mcp: [
    'task.list', 'task.next', 'task.update',
    'memory.search', 'memory.ingest',
    'checkpoint.create',
  ],
  // ... (5 vibe.* + 4 autopilot.* tools NOT listed)
};
```

The MCP server's `CallToolRequestSchema` handler (`server.mjs:197`) calls:

```javascript
assertToolAllowed(tool.name, 'mcp', defaultContracts);
```

This **throws an error** for any tool not in the allowlist. The result: calling `vibe.spec`, `vibe.plan`, `vibe.review`, `vibe.memory`, `vibe.merge`, `autopilot.start`, `autopilot.status`, `autopilot.list`, or `autopilot.stop` via MCP will return:

```
{"isError": true, "content": [{ "type": "text", "text": "Error: Tool \"vibe.spec\" is not allowed for adapter \"mcp\". Allowed: [task.list, task.next, task.update, memory.search, memory.ingest, checkpoint.create]" }]}
```

**Severity:** All 5 `vibe.*` command tools and all 4 `autopilot.*` tools are **non-functional via the MCP protocol** despite being registered and advertised.

## 2. Autopilot Runtime State Lifecycle

### 2.1 Persistence Path

**File:** `runtime/mcp/autopilot-tools.mjs:21`

```javascript
const STATE_DIR = '.vibe/runtime/autopilot';
```

Sessions are persisted as `.vibe/runtime/autopilot/<id>.json` via `writeSession()` (line 71-76). The `ensureDir()` helper (line 33-35) creates the directory tree on first write.

**Test:**
```
$ ls .vibe/runtime/autopilot/   # dir exists after first session creation
```

### 2.2 .gitignore Gap — CRITICAL

**File:** `.gitignore`

```gitignore
.omc/                    ← COVERED
# NO ENTRY FOR .vibe/    ← NOT COVERED
```

`git check-ignore` confirms:
- `.omc/runtime/tasks.json` → **ignored** (covered by `.omc/` rule)
- `.vibe/runtime/autopilot/audit.log` → **NOT ignored** (leaks to git)
- `.vibe/setup.json` → **NOT ignored** (already tracked, `git ls-files` confirms)

The `.vibe/` directory is also listed in `package.json` `"files"` array (line 20), meaning it would be included in npm publish. Sessions contain rule definitions, agent labels, and call statistics — potential information disclosure.

### 2.3 No Session TTL — MODERATE

`autopilot.start` creates sessions with a `createdAt` timestamp but **no expiration or TTL**. The `listSessions()` function (`autopilot-tools.mjs:91-99`) returns ALL `.json` files in the state directory regardless of age. Stale sessions accumulate indefinitely. There is no garbage-collection mechanism.

The `autopilot.stop` tool explicitly deletes state, but if the client crashes or disconnects, orphaned sessions remain forever with no reaper process.

### 2.4 Audit Log Integrity — ADVISORY

The `auditLog()` function (`autopilot-tools.mjs:40-46`) appends to `.vibe/runtime/autopilot/audit.log`:

```javascript
const line = `${new Date().toISOString()} | ${op.padEnd(12)} | ${String(id).padEnd(20)} | ${extra || ''}\n`;
await writeFile(logFile, line, { flag: 'a', encoding: 'utf8' });
```

**Concerns:**
- Append-only but **no integrity protection** (no HMAC, no checksum chain, no signing).
- The file is a flat text file, easily editable by anyone with filesystem access.
- No log rotation mechanism.

## 5. Security Gaps

### 5.1 Approval Gate Wiring

**File:** `runtime/core/approval-gate.mjs`

The `withApprovalGate()` middleware (line 239-272) wraps every MCP tool handler. It:
- Checks `requiresApproval()` against risk level and `ACTION_FORCE_APPROVAL` set
- Creates a pending approval record in `approvals.json`
- Requires explicit `approveAction()` or `denyAction()` to proceed
- Scopes approvals per-arg-set via `argsHash` (SHA-256 of sorted args, line 61-72)

**Unit tests: 15/15 PASS** — All approval lifecycle states covered (create, approve, deny, reuse pending, non-existent ID handling).

### 5.3 Contract Allowlist vs Tool Surface — CRITICAL

The `defaultContracts.mcp` allowlist (`tool-contract.mjs:8-15`) contains only 6 core tools. Since `assertToolAllowed()` is called for every MCP tool invocation (`server.mjs:197`), the 5 `vibe.*` and 4 `autopilot.*` tools are **registered but non-functional**.

This is a regression from v2.16.1 CHANGELOG claim: _"Wired 5 command tools (vibe.spec, vibe.plan, vibe.review, vibe.memory, vibe.merge) into the MCP server."_ The tools are wired into the tool list but blocked by the contract gate.

### 5.4 Audit Log Tampering

The `auditLog()` function in `autopilot-tools.mjs` writes to a plain-text file with no:
- HMAC signing or checksum chain
- Append-only enforcement (any process can truncate/edit)
- Read-back verification
- Log rotation or size limits

For a system that controls automated policy-based tool execution, this audit trail is legally insufficient for compliance purposes.

## 6. Recommendations

### P0 — Fix tool-contract.mjs MCP allowlist (Critical)
**File:** `runtime/core/tool-contract.mjs:8-15`
Add all 15 tools to the `mcp` adapter entry:
```javascript
mcp: [
    'task.list', 'task.next', 'task.update',
    'memory.search', 'memory.ingest',
    'checkpoint.create',
    'vibe.spec', 'vibe.plan', 'vibe.review', 'vibe.memory', 'vibe.merge',
    'autopilot.start', 'autopilot.status', 'autopilot.list', 'autopilot.stop',
],
```
Without this, the MCP server advertises but silently breaks 9 of 15 tools.

### P0 — Add `.vibe/` to `.gitignore` (Critical)
**File:** `.gitignore`
Add a single line:
```gitignore
.vibe/
```
This prevents autopilot sessions, audit logs, and setup manifests from leaking into version control.

### P1 — Fix `scripts/runtime-mcp.mjs --tools/--help` (High)
**File:** `scripts/runtime-mcp.mjs:26-28`
Add `buildAutopilotTools()` to both `printHelp()` and the `--tools` handler so the CLI introspection accurately reflects the full 15-tool surface.

### P1 — Add autopilot unit tests (High)
Create `scripts/test-autopilot-policy.mjs` with tests for:
- Policy `allows()`, `requiresApproval()`, `recordCall()`
- Wildcard matching (`*`, `prefix.*`, exact)
- Reserved pattern expansion (`write`, `network`, `dangerous`, `all`)
- Call-count limits and denial after max_calls exceeded
- Invalid rule rejection (bad risk level, bad approval value)
- `runLoop()` edge cases (null action, error in onExecute, autoApprove)

### P2 — Add session TTL / garbage collection (Medium)
Implement a stale-session reaper in `autopilot.start` or a standalone `scripts/runtime-autopilot-gc.mjs` that purges sessions older than a configurable TTL (default: 24h). Wire it into `listSessions()` to filter expired entries.

### P2 — Harden audit log for compliance (Medium)
Consider HMAC-signed audit entries or at minimum:
- Read-only mode enforcement via file permissions
- Size caps with automatic rotation
- Integrity check at startup (compare stored vs computed checksum)
