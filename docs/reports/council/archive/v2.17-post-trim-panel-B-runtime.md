## 1. Autopilot Stack Assessment

### 1.1 `runtime/autopilot/policy.mjs` (206 lines)

**Strengths:**
- Clean Policy class with `allow()`/`deny()` methods and action-level controls
- Subject matching (string, regex, array) covers most use cases
- Policy file loading with safe fallback to default-deny

**Concerns:**
- No persistence: policy is per-process, lost on restart. For a real "autopilot" this would need to save/load state.
- No audit log: allowed/denied actions aren't logged. Compliance gap.
- `validateRules()` exists but isn't called in `loadPolicy()`. If a user provides invalid JSON, errors will surface at `allow()` time, not load time.

**Verdict:** 🟡 **Functional but not production-hardened.** Works for single-session use, but autopilot implies long-running — needs state persistence.

### 1.2 `runtime/autopilot/loop.mjs` (135 lines)

**Strengths:**
- Integrates with `runtime/core/approval-gate.mjs` for checkpoint enforcement
- Stats tracking (iterations, approved, denied) for observability
- Clean exit on terminal state

**Concerns:**
- No integration with the MCP server (`runtime/mcp/server.mjs`). If user triggers autopilot from an MCP client, the MCP server has no autopilot tool registered.
- No integration with `runtime/daemon/daemon.mjs`. The daemon would need to load the autopilot loop to provide always-on automation.
- Scheduling engine mentioned in skill description is barely implemented (one sentence of "scheduling engine" — but no cron/timer integration visible).

**Verdict:** 🟡 **Loop is testable in isolation but not wired to runtime entry points.**

### 1.3 `adapters/hooks/autopilot-hook.mjs` (92 lines) and `adapters/claude-code/autopilot-hook.mjs` (134 lines)

**Strengths:**
- Generic adapter + Claude Code specific implementation
- Schema documented in code comments
- JSON output for SessionEnd hook matches v2.1.92+ format

**Concerns:**
- Generic hook has 92 lines but no `validate-policy.mjs` companion. Adapter-side validation would prevent bad policies from reaching the loop.
- Claude Code hook loads `policy.mjs` directly. If the path doesn't exist, the import will throw — error handling is "try/catch and log warning" but doesn't fall back to safe-deny.

**Verdict:** 🟡 **Adapters work but rely on the runtime layer being present.**

### 3.3 MCP Server — Missing Autopilot Tools

`runtime/mcp/server.mjs` does NOT register autopilot tools. A user with an MCP client (Claude Desktop, etc.) cannot invoke autopilot via the MCP protocol. This is a **functional gap**: autopilot exists in `runtime/autopilot/` but is not exposed as MCP tools.

**Fix:** Add to `runtime/mcp/command-tools.mjs`:
```js
{ name: 'autopilot_start', description: 'Start autopilot loop with policy file' }
{ name: 'autopilot_stop', description: 'Stop running autopilot loop' }
{ name: 'autopilot_status', description: 'Get current autopilot stats' }
```

---

**Summary:** The v2.17 build delivered a working autopilot stack at the file level (all 4 new files compile, no broken imports, all 10 validators pass). But the stack is **isolated from the MCP server** (no autopilot tools), has **no state persistence** (single-session only), and **no audit log**. A user testing autopilot from Claude Code via MCP would find the autopilot *exists* but is *not invocable* through the MCP tool surface. The runtime is **functionally complete for a single-session demo** but **not production-hardened for always-on use**.
