## Executive Summary

Vibe Coding OS v1.2.0 is stable as a markdown-first AI coding discipline framework. The release successfully closed the runtime-contracts-v2 foundation: strict item schemas, traceable runtime state, approval/event/tool-contract schemas, and migration dry-run support.

The expert council agrees on the next strategic direction:

1. **Do not become a CrewAI/LangGraph/OpenHands clone.** Vibe Coding OS should remain the discipline layer that works on top of Claude Code, Cursor, Codex, Gemini, Hermes, and other AI coding tools.
2. **v1.3 should close the gap between “contract exists” and “contract is enforced.”** Runtime contracts are well-designed, but enforcement paths, claim/lease behavior, approval gates, replay/recovery, and integration tests are still immature.
3. **Adoption UX is now the other major bottleneck.** The framework has strong depth, but new users need a faster “first workflow in 5 minutes” path, stack-specific skill packs, and proof of value through observable metrics.
4. **There are minor public-doc drift issues after v1.2.0.** The dashboard and roadmap status are broadly correct, but README “What’s new” sections and the v1.2 roadmap/archive status should be cleaned up before feature work.

Overall council verdict:

- Core framework maturity: **4.5/5**
- Runtime contract design: **4/5**
- Runtime production enforcement: **2/5**
- Adoption readiness for new users: **3/5**
- Differentiation: **4.5/5**

## Reviewer Findings

### R1 — Status is mostly correct, but README “What’s new” is stale

Evidence:

- `docs/DASHBOARD.md` reports v1.2.0 complete and 16/16 gates passing.
- `docs/ROADMAP-STATUS.md` reports v1.2 complete.
- However, README/README.vi still contain v1.1-oriented “What’s new” copy in the visible marketing section.

Impact:

- Low technical risk, medium adoption risk.
- Users landing on GitHub may think v1.2.0 is only a package bump rather than a runtime-contracts release.

Recommendation:

- P0 v1.3 cleanup: update README/README.vi “What’s new” to v1.2.0 and add a validation rule that this section matches `package.json` major/minor release.

### R2 — `docs/v1.2-roadmap.md` should be archived or marked complete

Evidence:

- Roadmap still describes v1.2 as future/current plan based on v1.1.
- `ROADMAP-STATUS.md` says v1.2 is complete.

Impact:

- Readers can confuse old planning artifacts with active roadmap.

Recommendation:

- Add an explicit “Historical roadmap — completed by v1.2.0” banner.
- Create `docs/v1.3-roadmap.md` as the new active planning artifact.

### R3 — v1.2 release notes should use final release wording

Evidence:

- Release notes are present and detailed, but some status wording still reads like release preparation.

Impact:

- Small trust issue in release docs.

Recommendation:

- Patch release notes with final validation baseline and “Released” wording.

### R4 — Runtime item schemas are strict, but collection/envelope strictness remains mixed

Evidence:

- Many `runtime-*.schema.json` item schemas now use strict top-level shapes.
- The collection envelope remains more permissive for compatibility.

Impact:

- Good for backward compatibility, weaker for the “strict contracts” claim.

Recommendation:

- v1.3 should formalize a strict collection envelope with explicit `metadata`/`extensions` escape hatches.

### R5 — Migration is a dry-run foundation, not production migration yet

Evidence:

- `scripts/runtime-migrate.mjs` exists and supports dry-run manifest generation.
- Apply/rollback/backup semantics are not yet strong enough to recommend unattended migration.

Impact:

- Runtime users may assume migration is safer than it is.

Recommendation:

- v1.3 should productionize migration: backup, apply, rollback, idempotency, post-migration assertions, and partial-failure semantics.

## Researcher Findings

### Positioning

Vibe Coding OS should be positioned as:

> The discipline layer for AI coding — a markdown-first workflow framework that makes Claude Code, Cursor, Codex, Gemini, Hermes, and other AI tools more reliable without replacing them.

This is meaningfully different from:

- CrewAI: Python multi-agent runtime framework
- LangGraph: stateful agent graph engine
- OpenHands: autonomous coding agent/runtime environment
- Cursor/Claude Code/Codex: AI coding tools/editors/CLIs

Vibe Coding OS should not compete on:

- Full autonomous runtime depth
- Graph DSL complexity
- Hosted agent environment
- IDE replacement

It should double down on:

- Spec-first workflow discipline
- Markdown-first portability
- Tool-agnostic adapter guidance
- Validation/evidence gates
- Memory/context discipline
- Team orchestration patterns
- Bilingual EN/VI onboarding
- Reference intelligence

### Missing adoption assets

The strongest adoption gaps are:

1. No high-signal real-world case studies.
2. No “first workflow in 5 minutes” guided path.
3. No stack-specific starter packs for common users.
4. No visible ROI/usage metrics.
5. Limited interactive/demo onboarding.
6. Skill discovery is still mostly inventory-driven, not problem-driven.
7. Community contribution path for skills is not prominent enough.

### Recommended differentiation themes

1. **First Workflow in 5 Minutes**
2. **Observable Workflow**
3. **Stack-Specific Skill Packs**
4. **Safety-First Multi-Agent**
5. **Community & Ecosystem Flywheel**

## Architect Findings

### Runtime maturity rating

Current runtime production-readiness: **4/10**

Breakdown:

- Schema completeness: **8/10**
- Store/file safety: **6/10**
- Runtime enforcement: **3/10**
- Multi-agent concurrency: **3/10**
- Approval/safety enforcement: **2/10**
- Event replay/recovery: **2/10**
- Migration production-readiness: **3/10**
- Behavioral integration tests: **2/10**

### Strengths

- Runtime v2 contracts now cover the right nouns: task, workflow-run, checkpoint, session, team, memory, action, event, approval, tool contract, migration.
- Common envelope fields (`createdBy`, `source`, `trace`, `risk`, `metadata`, `extensions`) are strong for auditability.
- Local runtime storage is significantly more structured than before.
- Dry-run migration foundation exists.

### Key gaps

1. **Enforcement layer is missing or too distributed**
   - Schemas define rules, but stores/adapters do not consistently enforce them before writes or actions.

2. **Claim/lease exists as schema, not behavior**
   - Need actual claim, heartbeat, lease expiry, renew, release, and conflict handling.

3. **Approval gates are not wired to dangerous action execution**
   - Approval schema exists, but MCP/tmux/daemon/action execution paths need enforcement.

4. **Tool boundary contracts are not yet operational**
   - Tool-contract schema should drive adapter input validation and denied-path/tool restrictions.

5. **Event log is not yet replayable**
   - Need replay, projection, snapshot, and recovery utilities.

6. **Migration is not production-grade**
   - Need backup/rollback/apply/idempotency/post-migration verification.

7. **Runtime tests are structural, not behavioral**
   - Need integration tests for claim conflicts, approval-required operations, denied path/tool calls, migration rollback, and replay recovery.

## Council Consensus

### Main decision

v1.3 should be a **Production Readiness + Adoption UX** release.

Not another pure schema release.

The release should convert v1.2’s strong contracts into operational guarantees, while making the framework easier to try and understand.

### Recommended v1.3 release theme

> v1.3 turns Vibe Coding OS from “contract-rich discipline framework” into “enforceable, observable, adoption-ready AI coding OS.”

### Priority split

- **P0:** Public status correctness and roadmap hygiene
- **P1:** Runtime enforcement, safety, migration, event replay, integration tests
- **P2:** First-workflow onboarding and stack-specific adoption packs
- **P3:** Community/discovery/positioning assets

- Contribution guide for skills.

## Risks

1. **Scope creep**
   - Runtime enforcement + adoption UX can become too large if shipped together without phased sprints.

2. **Over-positioning as a runtime competitor**
   - The project must avoid implying it replaces LangGraph/CrewAI/OpenHands.

3. **Contract drift**
   - Schemas, stores, CLI commands, docs, and validation gates can diverge unless v1.3 adds behavioral tests.

4. **User onboarding overload**
   - 90 skills and 68 commands are impressive but intimidating. v1.3 needs fewer, clearer paths.

---

## Recommended Release Strategy

Ship v1.3 in 4 PR-sized sprints:

1. **Sprint A — P0 Trust Cleanup**
   - Docs/status/validator hygiene.

2. **Sprint B — Runtime Enforcement Core**
   - Enforcement module, claim/lease, approval gates, tool boundaries.

3. **Sprint C — Runtime Recovery + Tests**
   - Migration apply/rollback, event replay/recovery, integration tests.

4. **Sprint D — Adoption UX**
   - First workflow, install-pack, project doctor, export adapters, Next.js pack.

---

## Final Council Recommendation

Start v1.3 with P0 cleanup, then move immediately into runtime enforcement. Adoption UX should begin once the runtime enforcement story is credible enough to demonstrate in real examples.

The best next implementation order is:

1. P0 docs/status cleanup.
2. P1 runtime enforcement core.
3. P1 tests/recovery/migration hardening.
4. P2 first-workflow + stack pack.

This order protects trust first, then turns v1.2 contracts into real guarantees, then markets those guarantees through simpler onboarding.
