## 3. Findings (ranked by severity)

### 🔴 CRITICAL — C1: 76% of skills have unknown maturity

**Reproduction:**
```bash
$ jq -r '.skills[].maturity' registry/skills.json | sort | uniq -c
    1 alpha
    1 draft
    1 experimental
    8 beta
   26 stable
  113 unknown
```

**Impact:** A user looking at the registry cannot tell which skills are production-ready vs experimental. The maturity field exists in the schema but is unfilled for 113/150. This breaks the "trust but verify" promise of the registry.

**Fix (v2.15.0):**
- `scripts/audit-skill-maturity.mjs` — heuristic-based auditor:
  - Skills with `last_reviewed` < 90 days → "stable"
  - Skills with `last_reviewed` 90-365 days → "beta"
  - Skills with `last_reviewed` > 365 days → "experimental"
  - Skills without `last_reviewed` → "unknown" (warn)
- Wire into `npm run validate:all`
- Update registry with audit results, preserve manual overrides via `registry/skill-maturity-overrides.json`

### 🔴 CRITICAL — C2: 88% of SKILL.md files lack YAML frontmatter

**Reproduction:**
```bash
$ find skills/ -name SKILL.md -exec sh -c 'head -c 3 "$1" | grep -q "^---" && echo "OK $1" || echo "MISSING $1"' _ {} \; | grep -c "MISSING"
131        # 131/149 = 88% lack proper YAML frontmatter
```

**Impact:** The `skills/authoring-skills/SKILL.md` (skill author guide) requires frontmatter (name, version, introduced_in, last_reviewed, category, tags, status). 88% of skills violate this. The validator that should catch this (`scripts/validate-skill-frontmatter.mjs` if it existed) is absent.

**Fix (v2.15.0):**
- Create `scripts/validate-skill-frontmatter.mjs` — fails if SKILL.md lacks required frontmatter fields
- Bulk-fix the 131 missing files using a template-based approach (preserve body, prepend/append frontmatter)
- Wire into `npm run validate:all` as a new gate
- Add test: `tests/skill-frontmatter.test.mjs` with 6 cases (positive/negative for each required field)

### 🔴 CRITICAL — C3: Zero skill test coverage

**Reproduction:**
```bash
$ find skills/ -name "test*.mjs" -o -name "*.test.mjs" | wc -l
0
$ find skills/ -path "*/examples" -type d | wc -l
0
$ find skills/ -name "fixture*" -type d | wc -l
0
```

**Impact:** A user cannot tell if a skill works without manually invoking it. There's no "skill-test-fixture" or "skill-example-output" pattern. Compare to `security/redact/redactor.mjs` which has 51 tests, `scripts/quality-engine.mjs` which has 22 gates, but skills are unverified.

**Fix (v2.15.0):**
- Add a SKILL.md test convention: `skills/<category>/<name>/test.mjs` (or `test/` subdir)
- Create `scripts/validate-skill-tests.mjs` — counts skills with test files, reports coverage %, fails if <80%
- Add a reference test for 5 high-value skills: `safe-refactor`, `adversarial-code-review`, `critique-pass-protocol`, `secure-coding-checklist`, `red-team-bypass`
- Create `templates/skill-test-template.md` (test outline) and `templates/skill-example-template.md` (worked example)

### 🟠 HIGH — H1: Templates have 3% frontmatter coverage (4/119)

**Reproduction:**
```bash
$ for f in templates/*.md; do head -c 3 "$f" | grep -q "^---" && echo "OK" || echo "MISSING"; done | grep -c "MISSING"
115        # 115/119 = 97% lack frontmatter
```

**Impact:** Templates are not first-class discoverable objects in the registry. They lack metadata, can't be filtered, can't be tracked for freshness.

**Fix (v2.15.0):** Add `registry/templates.json (or filesystem scan)` (or extend `registry/prompts.json`) with template metadata. Add `scripts/validate-template-frontmatter.mjs` with required fields: name, version, last_reviewed, category, use_with.

### 🟠 HIGH — H2: 4 orphan commands/skills/templates (memory-compression cluster)

**Reproduction:**
```bash
$ node scripts/validate-traceability.mjs --verbose 2>&1 | grep "Orphan"
- Orphan command: commands/vibe-anti-overengineer.md
- Orphan command: commands/vibe-memory-compress.md
- Orphan skill: skills/memory/memory-compression/SKILL.md
- Orphan template: templates/memory-compression-template.md
```

**Impact:** 4 items exist in inventory but no narrative markdown links to them. Users won't discover them. They've been orphans since v1.x.

**Fix (v2.15.0):** Either (a) link them in a new "Memory management" guide section, or (b) document them in a "Pre-existing orphans" list in `docs/orphan-inventory.md` and add to roadmap for v2.16.0 removal.

### 🟠 HIGH — H3: No `last_reviewed` policy — when was each skill last validated?

**Reproduction:**
```bash
$ grep -l "last_reviewed:" skills/ -r | wc -l
8
$ find skills/ -name SKILL.md -newer CHANGELOG.md -type f | wc -l
0
```

**Impact:** A skill shipped 6 months ago might reference APIs that no longer exist. There's no review cycle. The 8 skills with `last_reviewed` show the field works, but the policy is unenforced.

**Fix (v2.15.0):**
- Define policy in `docs/skill-review-policy.md` (review cycle: 90 days for `stable`, 30 days for `beta`, 7 days for `experimental`)
- Add `scripts/flag-stale-skills.mjs` — outputs `docs/reports/stale-skills.json` listing skills with `last_reviewed` > policy
- Wire into `npm run validate:all` as advisory (warn, don't fail)
- Bulk-update all 149 skills with `last_reviewed: 2026-06-20` baseline (since v2.14.0 is the latest audit)

### 🟡 MEDIUM — M1: 4 orphan + 7 missing frontmatter + 113 unknown maturity = registry is mostly a list of names

**Impact:** The `registry/skills.json` is a name + path + description, not a vetted inventory. Users can't filter by "stable + last reviewed 2026 + has test".

**Fix (v2.15.0):** Add `scripts/build-skill-index.mjs` — generates `docs/SKILL-INDEX.md` with sortable table (name, category, maturity, last_reviewed, has_test, has_example, narrative_links_count). This is the user-facing registry.

### 🟡 MEDIUM — M2: No way to invoke skills programmatically

**Reproduction:**
```bash
$ ls scripts/ | grep -i "invoke-skill\|run-skill\|skill-runner"
# 0 results
```

**Impact:** Skills are markdown files. To "use" one, you read it and follow its instructions manually. There's no `vibe skill adversarial-code-review --input file.diff` or similar. The 51 redact tests work because redactor is `.mjs`, but skills are not executable.

**Fix (v2.15.0):** Lower priority — out of scope. Note in roadmap for v2.16.0.

### 🟡 MEDIUM — M3: 21+ docs/guides with no central index

**Reproduction:**
```bash
$ ls docs/*.md | wc -l
70+       # 70+ markdown files in docs/, 21 are guides
```

**Impact:** Users don't know which guide to read first. `docs/README.md` exists but is mostly a list. No "I'm a new user / maintainer / contributor — start here" flow.

**Fix (v2.15.0):** Add a `docs/DOCS-INDEX.md` with role-based paths (User, Maintainer, Contributor, Security Auditor) → ordered guide list.

### 🟢 LOW — L1: No skill deprecation tracking in code

**Impact:** `registry/deprecation-tracker.json` exists but is it referenced from any validator? If a skill is marked deprecated, does the next validate warn?

**Fix (v2.15.0):** Add `scripts/validate-deprecations.mjs` — checks if deprecation-tracker entries are still in skills.json, fails if inconsistency.

### 🟢 LOW — L2: Skills have no "depends_on" / "conflicts_with" metadata

**Impact:** Some skills depend on others (e.g., `safe-refactor` requires `writing-plans`). No formal expression of this.

**Fix (v2.15.0):** Lower priority. Document in `docs/skill-composition-guide.md` (referenced from plan 2026-06-19).

### 🟢 LOW — L3: Commands have no "outputs" metadata

**Impact:** A command like `vibe-adversarial-review.md` likely produces a critique. But there's no `outputs: [critique.md]` field.

**Fix (v2.15.0):** Add `outputs` to command frontmatter schema. Update `scripts/validate-commands.mjs`.

## 5. Risks & dependencies

- **Risk 1:** Bulk-fix frontmatter (D2) could corrupt SKILL.md if template is wrong. Mitigation: dry-run mode first, diff review.
- **Risk 2:** Bulk-update `last_reviewed` (D6) is technically false (skills weren't reviewed today, just metadata-added). Mitigation: add comment "// bulk-updated 2026-06-20 by v2.15.0 audit".
- **Risk 3:** Adding 5 skill tests (D3) is a one-time effort, but maintaining 149 tests is a different problem. Mitigation: D3 is "foundation", not "complete coverage". Document roadmap.
