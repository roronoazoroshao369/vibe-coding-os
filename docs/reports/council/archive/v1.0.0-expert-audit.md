# Vibe Coding OS v1.0.0 — Expert Audit Report

> **Generated:** 2026-06-17
> **Methodology:** 3-role parallel audit (Reviewer / Researcher / Architect) using subagent isolation
> **Version audited:** v1.0.0 (commit 50f43ad) — 13/13 validation gates PASS, 9/9 CLI smoke PASS, 6/6 adapter smoke PASS

---

## Executive Summary

Vibe Coding OS v1.0.0 is a **genuinely strong v1.0 release** with a stable core workflow contract, comprehensive validation, and portable adapter coverage. All headline metrics are verified.

However, the audit found **3 High-severity issues** (all documentation/messaging), **12 Medium-severity issues** (schema drift, CLI coverage, adapter smoke depth), and **5 Low-severity issues**.

The **runtime layer** is assessed at **2.3/5 maturity** — a useful opt-in companion but not production-grade. Its schemas and implementation are out of sync, and validation is aspirational rather than enforced.

**Bottom line:** Release as v1.0.0 is justified for the **core markdown workflow**. The runtime should be clearly labeled **experimental** until v1.1 hardening.

## 1. Reviewer Agent: Schema, Adapter & CLI Audit

### 1.1 Schema Contracts

| Finding | Severity | Detail |
|---------|----------|--------|
| **S1** | Low | `validate-schemas.mjs` checks JSON validity + headings but does **not** run real JSON Schema validation against generated instances. Required fields like `name`, `purpose`, `workflow` in skill schema are only checked by markdown heuristics, not schema engine. |
| **S2** | Medium | Runtime `collection.schema.json` does not cross-reference item schemas by `kind`. A `kind: "tasks"` collection can contain arbitrary objects and still pass schema check. |
| **S3** | Medium | Runtime item schemas are intentionally permissive (`additionalProperties: true`, minimal `required`) — this is flexible but conflicts with "stable contract" language. |
| **S4** | Low | `reference-index.schema.json` is stronger than other schemas but `uniqueItems` does not guarantee unique `id` values (custom dup check in validator covers this). |

### 1.2 Adapter Conformance

| Finding | Severity | Detail |
|---------|----------|--------|
| **A1** | ✅ | All adapters (Claude Code, Codex, Cursor, Gemini, Memory) have READMEs with setup, workflow, validation, gotchas. |
| **A2** | **Medium** | CLI `vibe init` only supports `[claude-code, codex, cursor]` — **Gemini** is excluded despite being a first-class adapter. |
| **A3** | Medium | Adapter smoke tests are regex-based and shallow — they check file existence and heading presence but do **not** execute install snippets or verify CLI init. |
| **A4** | Low | Cursor smoke test label says "Install snippet references existing CLAUDE.md" but doc references `AGENTS.md` — passes because `CLAUDE.md` happens to exist. |
| **A5** | Low | Memory adapter docs exist but are not represented in compatibility matrix as a row, creating ambiguity about whether Memory is an adapter category or future-only interface. |

### 1.3 CLI Consistency

| Finding | Severity | Detail |
|---------|----------|--------|
| **C1** | Low | Three command surfaces (`/vibe-spec` plugin, `commands/vibe-spec.md` prompt, `vibe spec` CLI helper) are consistent but confusing — no single doc explains the naming model. |
| **C2** | Medium | CLI help omits Gemini from `init` tool list. |
| **C3** | Low | `spec --copy`, `plan --copy`, etc. write fixed filenames (`SPEC.md`, etc.) without checking for existing files — silent overwrite risk. No `--force` or `--dry-run`. |
| **C4** | **Medium** | CLI smoke tests (9/9) skip: `doctor`, `list-skills`, `list-commands`, `init`, invalid command, invalid adapter, `--copy` paths. The "9/9" claim is for a narrow subset. |

## 2. Researcher Agent: Comparative Analysis

### 2.1 What Vibe Coding OS Does Better

| Pattern | Vibe Advantage |
|---------|----------------|
| **CrewAI** | Portable orchestration without runtime dependency; adaptive workflow tiers prevent unnecessary multi-agent overhead; evidence-based merge readiness; attribution-aware delegation. |
| **LangGraph** | Human-readable workflow contract; lower adoption cost (markdown vs graph code); risk-scaled process tiers; cross-agent compatibility. |
| **OpenHands** | Clearer engineering process (spec/review/merge); tool-agnostic safety; better lightweight adoption; formal upstream adaptation hygiene. |
| **Cursor ecosystem** | Complete workflow lifecycle (intent→merge); reusable commands/skills/templates; artifact persistence; cross-tool portability. |
| **Claude Code ecosystem** | Excellent alignment with `CLAUDE.md`, plugin, MCP, skills; strong modular context discipline; MCP kept optional; safety/attribution guidance. |
| **Codex CLI** | Strong adapter; good delegation guidance; skills as scoped procedures; validation-aware automation. |

### 2.2 Key Gaps Versus Ecosystem

| Pattern | What Vibe Is Missing |
|---------|----------------------|
| **CrewAI** | Machine-readable role/task schema; built-in orchestration semantics; role capability contracts; team execution observability. |
| **LangGraph** | Explicit workflow state machine; durable checkpoint semantics; conditional routing; replay/resume model. |
| **OpenHands** | Sandbox execution policy; action observation model; environment capability declaration; rollback/isolation mechanics. |
| **Cursor ecosystem** | First-class Cursor rule packaging (per-module rules); IDE context strategy; rule composition guidance. |
| **Claude Code ecosystem** | Deeper plugin lifecycle model; broader MCP tool surface; subagent role templates; portable hook contract. |
| **Codex CLI** | Nested `AGENTS.md` generation; scoped instruction conflict detection; Codex final-response templates. |

### 2.3 Strategic Positioning for v1.1

> **A portable workflow contract and artifact system for AI-assisted engineering, with optional local runtime state, adapter-native packaging, and verification-grade evidence.**

Vibe should **not** try to become CrewAI as a runtime orchestrator, LangGraph as a graph engine, OpenHands as a sandboxed environment, or Cursor as an IDE pack. Its portable workflow contract + verification discipline is the unique value.

## 3. Architect Agent: Runtime Layer Maturity

### 3.1 Maturity Scores

| Area | Score (1-5) | Summary |
|------|-------------|---------|
| State Schemas | **2.0** | Permissive, minimal, and — critically — **schemas do not match actual implementation** |
| Runtime CLI Scripts | **2.5** | Simple and readable but lacking error handling, argument validation, consistent output format |
| MCP Server | **2.5** | Good opt-in design but docs/tool-names/installer-config are inconsistent |
| Daemon Architecture | **2.5** | Appropriate for local use but PID race, stale heartbeat, no supervision |
| Team Runner (tmux) | **2.0** | Proof-of-concept; has command injection risk and run-identity issues |
| Schema-to-Instance Validation | **1.5** | `runtime-validate.mjs` does not use JSON Schema to validate items — worst area |
| Runtime vs Core Boundary | **4.0** | Best area; the opt-in boundary is well documented and respected |
| **Overall Runtime** | **2.3** | Prototype quality — not production-grade for v1.0 |

### 3.2 Critical Schema-Implementation Mismatches

| Area | Schema Says | Runtime Writes | Impact |
|------|------------|----------------|--------|
| Task status enum | `pending, running, done, failed, skipped` | `pending, in_progress, blocked, completed, cancelled` | Full contract break |
| Task field name | `name` | `title` | Schema validation would reject real data |
| Session fields | `label, startedAt, endedAt` | `goal, summary, createdAt, updatedAt` | Schema describes different model |
| Checkpoint required | only `id` | `type, result, subject, notes, createdAt` all present | Validation too weak |
| Team required | only `id` | `name, pattern, goal, roles, tasks, source` all present | Validation too weak |

### 3.3 Production-Readiness Blockers

1. **Schemas do not match implementation** (task status enum, field names)
2. **Runtime validation does not validate item schemas**
3. **Task status enum conflict** across schema/store/MCP/docs
4. **Session schema** describes a different object than runtime writes
5. **MCP docs/tool names/installer config** are inconsistent
6. **Daemon PID lifecycle** is race-prone and vulnerable to PID reuse
7. **tmux runner** has command injection risk and run-identity issues
8. **No migration/versioning strategy** beyond `schemaVersion = 1`
9. **No automated tests** for runtime state/schema conformance
10. **Missing schemas** for event log, vector index, daemon heartbeat, config, team-run outputs
