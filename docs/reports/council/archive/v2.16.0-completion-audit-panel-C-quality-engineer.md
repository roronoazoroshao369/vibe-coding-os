### 1.1 Quality Engine Sub-Gate Breakdown

Gate #31 (`quality-engine.mjs --profile=lean`) is itself a gate runner that spawns up to 38 additional sub-gates. With `--profile=lean`, only 4 sub-gates execute:

- `repo-structure`, `injection-scan`, `secret-scan`, `quality-diff-audit`

The remaining 30+ gates are marked **"advisory (skipped)"** — they appear in output but do not affect the exit code. The engine exits 0 even when skipped sub-gates would fail. This means **the quality engine gate (#31) provides almost no independent coverage beyond what validate-all already checks** — it re-runs the same `validate-repo.mjs` and `validate-injection.mjs` scripts that are already gates #1 and #6.

## 2. Reliability Assessment

### 2.1 False Positive (FP) Risk

**Injection scan (#6):** One confirmed FP on `docs/ROADMAP-STATUS.md` line 443. The file documents injection-related capabilities and legitimately quotes payload patterns. Despite allowlisting `docs/workflows/prompt-injection-handling.md` and `runtime/core/injection-patterns.mjs`, the ROADMAP file is not allowlisted — creating a known FP path that recurs with every status update. The gate also scans `docs/` directory broadly, which includes council reports that naturally discuss injection topics.

**Property tests (#36):** 68/382 tests fail (82.2% pass rate, above the 80% threshold but below a healthy baseline). Analysis of failures:
- **52 failures from `no_markdown_issues`**: The HTML-tag heuristic (`property-test-runner.mjs` line 187–192) flags files containing `<table>`, `<div>`, `<p>`, or `<h1>`–`<h6>` tags as "possible markdown violation." This is too aggressive — HTML in markdown is idiomatic for tables in many generators and for `details`/`summary` blocks. The heuristic has no allowlist or context-awareness.
- **16 failures from `no_placeholder_content`**: Flags intentional template placeholders like `[Title]`, `[YYYY-MM-DD]`, `[Goal]` in `adr-template.md`, `prd-template.md`, `roi-metrics-template.md`, etc. Templates *are supposed to have placeholders* — this test cannot distinguish template files from documentation.

**Quality engine (#31):** With `--profile=lean`, the engine prints **"Result: FAIL"** in its output when advisory gates would fail, yet exits with code 0. This is a UX hazard — downstream consumers parsing the text output see "FAIL" and may treat the run as failed, while the exit code says it passed.

**Provenance gate (#25):** The script header (`validate-provenance.mjs` lines 4–13) explicitly states: *"SELF-ATTESTED, NOT VERIFIED. This gate proves that every non-merge commit carries the required provenance trailers... It does NOT — and cannot — verify the claim is true."* A pass means "the author declared provenance", not "provenance is correct." This is honest but creates a false-sense-of-security risk.

### 2.2 False Negative (FN) Risk

**Trust scorer (#33):** `tests/security/trust-scorer.test.mjs` calls `scoreSource()` and asserts only that the return object has `trust_class` and `risk_score` properties. It does not assert *what score* a known-malicious input receives. A broken scorer that always returns `{ trust_class: 'trusted', risk_score: 0 }` would pass this test.

**Property test fuzzing (`property-test-runner.mjs` line 583):** The runner admits: *"Currently validates that the generated inputs are well-formed. Future: pass generated inputs through actual skill/command/template parsers."* The fuzz testing does not exercise any real parsing logic — it only checks that its own generator produces non-null combinations. This is a structural test disguised as a property test.

**RTL coverage (#34):** Validates that pattern coverage is 100%, but does not test whether the patterns actually *catch* real Bidi attacks — only that the test corpus references all defined patterns.

**Security regression (#27):** `tests/security/regression.mjs` is a real behavioral test but only covers injection scenarios. No regression tests exist for the redactor's 3 redaction modes, trust scorer edge cases, or sandbox marker logic.

Property tests add structural coverage but, as noted in §2.2, do not exercise real parsing or behavior.

### 3.2 Critical Coverage Gaps

1. **No runtime behavior gate.** Despite `runtime-behavior-tests.mjs` being gate #23, no gate validates that runtime scripts (`runtime-init.mjs`, `runtime-task.mjs`, `runtime-session.mjs`, etc.) actually perform their documented behavior. The behavioral test file exists but its coverage scope is not verified.

2. **No redactor behavioral test.** `validate-redact.mjs` tests that secrets are caught, but no test verifies the 3 redaction *modes* (block, redact, log) produce different outputs for the same input. The redactor module has mode-dependent logic that is entirely untested at the behavioral level.

3. **No concurrent-execution gate.** `validate-all.mjs` runs all 38 gates in parallel (`Promise.all`) but no gate validates that concurrent runs produce consistent results. Race conditions in shared output files (`/tmp/property-test-result.json`) could cause intermittent failures.

4. **No performance gate.** No gate asserts that validation completes within a time budget. The 38 gates ran in 15.5s this run, but no threshold prevents regression to 60s+.

5. **No license compatibility check.** `validate-licenses.mjs` checks license headers in source files but does not verify that `node_modules/` packages are MIT-compatible with the project's MIT license. A GPL dependency would pass all gates.

6. **Skill discovery is gate-blind.** None of the 38 gates validate that skills declared in `registry/skills.json` are actually present, or that `skills/core/INDEX.md` accurately reflects the current skill tree. A renamed or removed skill file could go unnoticed.

## 4. Test Quality

### 4.1 Test Harness Analysis

**23 test files** exist under `tests/`. Their quality varies significantly:

**Strong tests (behavioral, with real assertions):**
- `tests/security/regression.mjs` — real injection payloads, real behavioral assertions
- `tests/security/canary-corpus.test.mjs` — tests canary payload detection
- `validate-redact.mjs` (run as gate #28) — constructs test secrets, asserts redaction
- `tests/hooks/posttool-redactor-wiring.test.mjs` — integration-level test

**Weak tests (structural, shape-checking only):**
- `tests/security/trust-scorer.test.mjs` — calls `scoreSource()` with any content, asserts only return shape `{ trust_class, risk_score }`. Does not test adversarial inputs or scoring accuracy.
- `tests/commands/command-structure.test.mjs` — likely checks file format, not command behavior
- `tests/templates/template-schema.test.mjs` — schema conformance, not content quality
- Most Wave B tests are "existence-and-keyword" checks (verify a file exists and contains certain keywords)

### 4.2 Property Test Assessment

The property test runner (`scripts/property-test-runner.mjs`, 660 lines) is sophisticated in design but weak in execution:

- **Generator is structural:** Lines 575–603 show fuzz testing generates random input combinations but only checks they are non-null. No generated input is passed through any real parser.
- **Invariant checking is deferred:** Line 569: *"Custom invariant — structural validation deferred to test definition."* Custom invariants are recorded but never actually evaluated.
- **Two systematic FP patterns** (HTML tags, placeholders) account for 68/382 failures. These are not random — they occur on the same files every run, inflating the "pass rate" with known-false failures.

## 5. Recommendations for v2.17.0

### Priority 1: Close Security Test Gaps (High Impact, High Confidence)

1. **Add behavioral tests for trust scorer.** Test that known-malicious patterns (Bidi characters, encoded payloads, social-engineering prompts) receive lower trust scores than benign content. Test that `detectBypassLoop` catches circular trust escalation.

2. **Add redactor mode behavioral tests.** Verify that the same input produces different output under `block`, `redact`, and `log` modes. Verify that `postTool` mode does not mutate the original input.

3. **Add redactor integration test for the full 30×3 matrix.** `validate-redact.mjs` already does this for secrets — extend the pattern to test all redaction modes including the `log` mode's side-channel behavior.

### Priority 2: Fix False Positive Noise (High Impact, Medium Confidence)

4. **Triage the `no_markdown_issues` HTML heuristic.** Options: (a) add an allowlist for known-safe HTML tags (`<details>`, `<summary>`, `<table>`), (b) restrict the check to only skill/command files (exclude templates), or (c) lower the severity from "failure" to "warning" and decouple it from the 80% threshold.

5. **Triage the `no_placeholder_content` heuristic.** Add a file-pattern exception for `*template*` files, or invert the logic: only flag placeholder content in non-template files. Currently 16 template files are systematically flagged.

6. **Fix quality engine text-vs-exit-code mismatch.** When `--profile=lean` skips advisory gates, the output should say "PASS (N skipped advisory)" not "FAIL." Or decouple advisory output from the result line entirely.

### Priority 3: Close Coverage Gaps (Medium Impact, Medium Confidence)

7. **Add a performance budget gate.** Assert that `validate:all` completes within 30s. Use the existing `benchmark:gates` infrastructure to track regression.

8. **Add a concurrent-execution test.** Run `validate:all` twice simultaneously and assert both exit 0 with consistent output. This catches race conditions in shared temp files.

9. **Add license compatibility check.** Scan `node_modules/` for GPL/AGPL packages and fail if found. This is a single `find` + `grep` command.

10. **Add a skill-command-template consistency gate.** Cross-reference `registry/skills.json` entries against `skills/*/SKILL.md` files. Cross-reference `commands/manifest.json` entries against `commands/vibe-*.md` files. Fail on orphaned registry entries.

### Priority 4: Improve Test Infrastructure (Lower Impact, Higher Effort)

11. **Replace the property test HTML heuristic with a targeted check.** Instead of flagging any HTML tag, specifically flag `<script>`, `<style>`, `<iframe>`, or `<object>` tags that would be dangerous in a skill/command context. Allowlist `<table>`, `<details>`, `<summary>`.

12. **Wire real parsers into the fuzz harness.** The `property-test-runner.mjs` line 584 aspiration ("Future: pass generated inputs through actual skill/command/template parsers") should become a v2.17.0 deliverable.

13. **Add integration tests for the 8 lifecycle skill groups.** The 152 skills in `skills/core/INDEX.md` are organized into 8 groups (ideation → spec → planning → execution → quality → security → memory → merge). Add at least one end-to-end behavioral test per lifecycle group.

## Summary

v2.16.0's 38-gate validation pipeline covers breadth well — 7 categories, parallel execution, reasonable timeout. However, **depth is the weakness**: only 4 of 38 gates execute real behavioral logic. The remaining 34 are structural checks (file existence, regex scans, schema validation) that catch formatting and naming issues but not functional regressions. The security layer (injection scanner, redactor, regression tests) is the strongest subsystem, yet even here the trust scorer test is a shape-only assertion that would not catch a broken scorer. Property tests provide structural coverage but their two dominant failure modes (HTML heuristic, placeholder heuristic) are systematic false positives that inflate noise. The biggest gap is the 374-artifact / 17-tested-artifact imbalance — 4.5% direct coverage is insufficient for a framework that prescribes quality discipline to its users. v2.17.0 should prioritize behavioral test depth over gate count expansion.
