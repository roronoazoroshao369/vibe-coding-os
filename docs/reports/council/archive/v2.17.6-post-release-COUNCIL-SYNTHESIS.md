## Critical Gaps

### Gap 1: MCP auth end-user documentation (HIGH)

**Description:** `docs/workflows/runtime-mcp-server.md` describes 6 basic tools and registration in `.mcp.json`. It does NOT mention the auth handshake, `MCP_AUTH_TOKEN` env var, auto-generated token at `~/.vibe/mcp-token`, or the `_mcp.auth.verify` call. A newcomer using Claude Desktop will hit "Not authenticated" with no path to resolution.

**Fix:** Add a "## Authentication" section to `docs/workflows/runtime-mcp-server.md` covering:
1. How auth works (token-gated handshake)
2. Auto-generated token (what happens when no env var is set)
3. How to configure (env var or file)
4. All 11 tools listed in the provided tools table (not 6)
5. Link to SECURITY-MODEL.md for threat model details

### Gap 2: MCP auth test not wired into CI (MEDIUM)

**Description:** `tests/runtime/runtime-mcp-auth.test.mjs` has 25/25 PASS but is not included in any CI workflow or npm test script. The test file only runs when manually invoked. A regression in the auth code would not be caught by the quality gate.

**Fix:** Add `"test:auth": "node tests/runtime/runtime-mcp-auth.test.mjs"` to `package.json` scripts. Wire into `pr-quality-comment.yml` or `quality-gates.yml` as a new job.

### Gap 3: Token resolution priority untested (MEDIUM)

**Description:** `resolveAuthToken()` has 3-level precedence (env → file → auto-generate). The existing test covers each path in isolation but never tests the priority chain — e.g., what happens when `MCP_AUTH_TOKEN` is set to an empty string? Does it fall through to the file, or return the empty string as a valid token?

**Fix:** Add test case for empty-string env var fallthrough.
