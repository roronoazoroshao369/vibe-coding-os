## 1. Pipeline Health

### 1.1 `npm run validate:all` — what actually runs

`package.json` chains 12 validators, all of which run on every `validate:all`:

```
validate-repo → validate-references → validate-traceability → validate-injection
  → validate-imports → validate-typecheck → validate-scope-match
  → validate-secrets → validate-licenses → validate-provenance
  → validate-no-deprecated-commands → validate-orphans
```

**Observed outcome on a clean working tree:**

| validate-references | ✅ PASS | 22 sources, 25 feature docs, 4 mapping docs, 5 reference commands |

**Net result: 11/12 PASS, 1 FAIL → `validate:all` exits 1, so the headline is misleading.** The CHANGELOG for v2.17.6 calls this "12 gates" and Panel A's "all green" claim inherits from the same command — both are wrong against current disk.

### 1.2 Theater assessment (non-theater verification)

I checked each gate for "always-pass" theater by examining whether its count actually moves when a real defect is introduced. Specifically:
- `validate-traceability` was confirmed against the v2.17.4 fix where it caught the `vibe-specify` / `vibe-parallel-explore` stale refs across 7 files. **Not theater.**
- `validate-injection` scans 600 text files and 1 MCP manifest and has a separate blocking/warning policy wired into the runtime (`server.mjs` lines 78–96). **Not theater.**
- `validate-no-deprecated-commands` was extended in v2.17.5 to cover `.claude-plugin/` and `skills/`; it catches the same set of stale refs the older tooling missed. **Not theater.**
- `validate-orphans` is **non-blocking and exit 0 always** — it cannot fail the build. It is a true catalog-honesty warning system (allowed-orphan allowlist for category-index SKILL.md files). **Not theater, but also not a gate.**
- `validate-secrets` produces 7 hits against *tracked* files that contain the word "token" in code comments. **Partial theater** — pattern is over-greedy and is being ignored in practice (see §3.4).

**Verdict: the pipeline is real, but the failure mode in §1.1 means it is currently red on every commit.** Any maintainer landing a PR will see a broken `validate:all` for reasons unrelated to their change.

## 2. Test Suite Quality

### 2.1 `tests/runtime/runtime-mcp-auth.test.mjs` (v2.17.6 deliverable)

- **Result:** 25 passed / 0 failed (own run).
- **File length:** 238 lines, well-structured (8 numbered sections in header comment).
- **Coverage shape:**
  - `defaultContracts.mcp | hermes | ai-assistant` include `_mcp.auth.verify` ✅
  - `assertToolAllowed` accepts the new tool under all three contracts; rejects unknown tools ✅
  - `loadSdk()` returns `Server/StdioServerTransport` **or null gracefully** (i.e., it tolerates the dependency being absent — good for opt-in runtime) ✅
  - `buildTools()` returns the documented core set with risk metadata + inputSchema ✅
  - `INJECTION_PATTERNS` is asserted to contain `error` + `warn` severities, `instruction-override` + `role-reassignment` (adversarial coverage), and the `mcp-shell-exec` pattern with `scope=mcp` ✅
  - End-to-end `scanArgumentsForInjection`: 5 known-bad payloads (block) + 1 known-warning + benign + non-object args (9 cases total) ✅
- **False positives:** none observed; benign input correctly passes.
- **What's missing (gaps a future contributor would care about):**
  1. **No real stdio round-trip test.** The header comment acknowledges this and argues the SDK is loaded statically. A future regression in the request-handler wiring (e.g., auth-check ordering, the `appendEvent` try/catch) would slip through. Low priority given the `validate:secrets` + injection-scan production paths are tested by `validate:injection` already.
  2. **No test for token-resolution priority order** (env > file > auto-generate). The behavior is non-trivial (writes to disk with 0o600) and a regression would be a security incident. **Medium priority — should be added in v2.17.7.**
  3. **No test for the `appendEvent` failure path** (the CHANGELOG explicitly calls it "best-effort" / not a hardened audit pipeline). At minimum a smoke test asserting the call is wrapped in try/catch would be a regression guard. Low priority.
  4. **No test asserting the auto-generated token file is actually `0o600`.** A permission regression on `writeFile` would not be caught. Medium priority.
