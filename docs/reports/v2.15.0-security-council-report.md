## 3. Findings (ranked by severity)

### 🔴 CRITICAL — C1: PostToolUse hook is 5 months behind the redactor

**Reproduction:**
```bash
$ grep -c "security/redact/redactor" .claude/hooks/post-tool-use-secret-scan.mjs
0
$ head -20 .claude/hooks/post-tool-use-secret-scan.mjs | grep "PATTERNS"
const SECRET_PATTERNS=***[
  { id: 'aws-key',     regex: /AKIA[0-9A-Z]{16}/g },
  { id: 'github-pat',  regex: /github_pat_[0-9a-zA-Z_]{50,}/g },
  { id: 'openai-key',  regex: /sk-[0-9a-zA-Z]{20,}/g },
  # ... 5 more inline patterns
];
```

**Impact:** v2.14.0 shipped 30-pattern redactor with 97.37% OWASP LLM01 coverage. The hook still uses 8 patterns from v1.x. When a user pastes an Anthropic API key (`sk-ant-api03-...`), the new redactor catches it; the hook does not. The new redactor is effectively a library, not a runtime safeguard.

**Fix (v2.15.0):**
- Refactor `.claude/hooks/post-tool-use-secret-scan.mjs` to import `security/redact/redactor.mjs` (postTool mode)
- Same refactor for `user-prompt-submit-injection-scan.mjs` (postSession mode) and `pre-tool-use-default-deny.mjs` (postPublish for outbound allowlist checks)
- Add a regression test: `tests/hooks/posttool-redactor-wiring.test.mjs` that asserts the hook's behavior matches the redactor's behavior on the same fixture set

### 🔴 CRITICAL — C2: Sandbox-marker is convention-only, not enforced

**Reproduction:**
```bash
$ grep -l "sandbox-marker" skills/ -r | wc -l
1   # Only the skill's own SKILL.md references it
$ grep -l "fetch.*url\|http.get" skills/*/SKILL.md -r
skills/core/sandbox-marker/SKILL.md
skills/prompts/code-complete-construction/SKILL.md
# 2 skills fetch external content, 0 use sandbox-marker
```

**Impact:** `skills/prompts/code-complete-construction/SKILL.md` reads external URLs without sandbox-marker prefix. This is the exact anti-pattern the v2.14.0 sandbox-marker skill was created to prevent. The convention is documented but not enforced.

**Fix (v2.15.0):**
- Add `scripts/validate-sandbox-marker.mjs` — fails validation if a SKILL.md has `fetch(`, `http.get`, `axios.`, or `requests.get` without an adjacent "sandbox-marker:" header
- Wire into `npm run validate:all`
- Fix the 1 known offender (`skills/prompts/code-complete-construction/SKILL.md`)

### 🟠 HIGH — H1: Bypass authorization gate has no rate-limit or abuse detection

**Reproduction:**
```bash
$ cat docs/security/bypass-load-attempts.log
# 3 entries total: 1 refusal-env-missing, 1 refusal-no-authorization, 1 authorized-load
# All 3 from same minute (2026-06-20T02:51:06) — synthetic test, not real traffic
```

**Impact:** The gate logs but does not enforce rate limits. An attacker (or buggy CI) can spam `VIBE_ENABLE_OFFENSIVE_TECHNIQUES=1 vibe bypass-load --authorization-ref=foo` indefinitely. There's no per-PID throttle, no per-authorization-ref throttle, no alert when same `authorization_ref` is reused >N times.

**Fix (v2.15.0):**
- Add rate-limit to `scripts/load-bypass-techniques.mjs`: 10 loads/min per authorization_ref, 60 loads/hour globally
- Add `docs/security/bypass-rate-limit.md` documenting thresholds
- Add `scripts/validate-bypass-attempts.mjs` — counts attempts in last 24h, fails CI if abnormal

**Fix (v2.15.0):** Wire postSession into `session-end-audit-flush.mjs`. Wire postPublish into a new `vibe share` command (or similar). Add `docs/redactor-modes.md` mapping each mode to its consumer.

## 5. Risks & dependencies

- **Risk 1:** Hook refactor (D1) might break existing Claude Code users. Mitigation: keep hook entrypoint names stable, change internals only.
- **Risk 2:** Sandbox-marker enforcement (D2) might fail on skills that legitimately fetch without sandboxing (e.g., red-team-bypass). Mitigation: allowlist file for skills that explicitly opt out.
- **Risk 3:** Rate-limit on bypass load (D4) might break CI pipelines that rely on unbounded loads. Mitigation: env var override `VIBE_BYPASS_RATE_LIMIT=unbounded` for CI with `--ci` flag.

---

## 6. Recommendations

1. **Adopt this v2.15.0 plan as-is** — 6 deliverables, all 3 critical, ~150KB of new/modified files, ~2 weeks of focused work.
2. **Sequence:** D1 (hooks) and D2 (sandbox) are independent → parallelize. D3 (commands) and D5 (license) are independent → parallelize. D4 (rate-limit) and D6 (adapter wiring) are independent → parallelize. 3 parallel teams.
3. **Add regression tests** for every D1/D2/D4/D6 deliverable. The pattern of "shipped but unwired" we just found must not repeat.
4. **After v2.15.0:** security posture should be 8.0/10. Then v2.16+ can focus on adapter breadth + community.

**Final score:** 6.4/10. Target after v2.15.0: 8.0/10.
