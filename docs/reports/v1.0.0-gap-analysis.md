## 1. Skill Quality and Depth — **4.0 / 5**

### What is strong

- 90 skills across core, memory, agents, prompts, meta.
- Strong engineering workflow coverage: clarification, spec-first, TDD, diagnosis, review, branch finishing, memory, upstream attribution.
- The repository has moved beyond prompt-pack quality into workflow-system quality.
- Skills support the core workflow contract: Intent → Spec → Plan → Implement → Test → Review → Memory → Merge.
- Category distribution is coherent: core skills dominate, memory and prompts are meaningful supporting layers.

### Gaps

1. **Quality is validated structurally, not behaviorally**
   - `validate:repo` checks required sections and references.
   - It does not measure whether a skill produces better implementation outcomes.

2. **Skill selection metadata is underdeveloped**
   - Skills lack machine-readable fields such as:
     - phase (`intent/spec/plan/...`)
     - task tier (`tiny/small/medium/large/risky`)
     - prerequisites
     - incompatible skills
     - expected output artifact

3. **No skill dependency graph**
   - Some skills clearly depend on others (e.g. checkpoint validation before implementation readiness), but there is no graph to warn about missing precursor skills.

4. **No per-skill evaluation scenarios**
   - The repo has eval scenarios, but not enough skill-level acceptance tests.

### Improvements

- Add `skill-metadata.schema.json` or extend `skill.schema.json` with:
  - `phase`, `tier`, `triggers`, `prerequisites`, `outputs`, `related_templates`, `verification`.
- Add `vibe recommend-skills` based on task phase/tier.
- Add 10-20 golden path eval scenarios where skill use should change the output.
- Add "bad output avoided" examples for core skills.

## 2. Command Prompt Usefulness and Specificity — **3.8 / 5**

### What is strong

- 68 commands provide broad coverage for the lifecycle.
- CLI helper maps common command intents (`spec`, `plan`, `memory`, `task`, `templates`).
- Commands appear aligned with local templates and skills.
- CLI smoke tests confirm core prompt outputs are printable and non-empty.

### Gaps

1. **Command surfaces are confusing**
   - There are at least three surfaces:
     - Claude slash command: `/vibe-spec`
     - markdown prompt file: `commands/vibe-spec.md`
     - CLI helper: `vibe spec`
   - Docs do not explain this clearly enough.

2. **Smoke tests cover only a subset**
   - `doctor`, `list-skills`, `list-commands`, `init`, failure paths, and copy modes are not covered.

3. **Output contracts vary**
   - Some commands ask for artifacts, but not always with explicit "must include" fields, failure criteria, or evidence block.

4. **No command-to-skill recommendation map**
   - Command prompts could explicitly say which skills/templates should be loaded for each phase.

### Improvements

- Add a "Command Surfaces" doc section in README + CLI help.
- Expand CLI smoke to all advertised commands and negative cases.
- Add a future command manifest or generated command metadata:
  - `slug`, `phase`, `default_template`, `recommended_skills`, `output_contract`.
- Add tests that command references only existing skill/template paths.

## 3. Template Completeness for Real-World Use — **4.0 / 5**

### What is strong

- 41 templates cover spec, plan, task, PRD, ADR, architecture review, review, diagnosis, memory, session summary, handoff, upstream audit, scorecard, team spec, runtime config.
- Templates map well to the v1.0 core workflow.
- Practical for real use, not merely illustrative.
- Good bilingual/onboarding support around key flows.

### Gaps

1. **Traceability template is missing/underpowered**
   - No formal template maps acceptance criteria → plan steps → tasks → changed files → tests → checkpoints.

2. **Evidence/checkpoint templates are not strong enough**
   - Runtime checkpoint schema is weak; template should require command, output, status, limitations, and resume hints.

3. **Team-run artifact template is not mature**
   - Multi-agent work needs stricter role-output and integrator-review templates.

4. **Adapter-specific templates are limited**
   - Cursor rules pack, Codex final response, Claude subagent role templates could improve adoption.

### Improvements

- Add `templates/traceability-map-template.md`.
- Upgrade checkpoint/evidence templates.
- Add a future team-run output template and a future integrator review template.
- Add adapter-specific template packs:
  - Cursor `.cursor/rules` pack
  - Codex final response pack
  - Claude subagent role pack

- Add adapter reference/path link checker.
- Add adapter support matrix for:
  - setup path
  - CLI init support
  - smoke coverage
  - plugin/native package status
  - known limitations

## 5. Runtime Layer Production-Readiness — **2.3 / 5**

### What is strong

- Runtime is correctly opt-in.
- Local JSON state keeps data inspectable.
- No mandatory database/daemon/MCP dependency.
- Boundary docs correctly protect the markdown-first core.
- Runtime concepts (task/memory/checkpoint/team/session/MCP/daemon) are directionally valuable.

### Gaps

1. **Schema/runtime mismatch**
   - Task schema uses `name`; runtime writes `title`.
   - Task schema status enum differs from runtime store.
   - Session schema describes different fields than runtime writes.

2. **Validation is not real item validation**
   - `runtime-validate` checks collection envelope only.
   - It does not validate each item against schema.

3. **Missing cross-reference validation**
   - No duplicate ID checks across runtime collections.
   - No task dependency integrity checks.
   - No team role/task relationship validation.

4. **MCP docs mismatch implementation**
   - Docs list `vibe_task_list`, etc.; implementation uses `task.list`, etc.
   - Docs promise task create; implementation surface differs.

5. **Daemon not production-grade**
   - PID race conditions, stale heartbeat risk, PID reuse risk, no wait-for-stop.

6. **tmux runner risks**
   - Command injection risk via `--command`.
   - `collect` rebuilds new run descriptor instead of using persisted run ID.
   - Kills existing sessions by default.

### Improvements

- Treat runtime as **experimental** until v1.1 hardening completes.
- Align schemas with implementation.
- Add real JSON Schema validation (Ajv or strict local validator).
- Add item-level and cross-file validation.
- Add runtime conformance smoke tests.
- Add team-run descriptor persistence and safer command execution.

## 6. Reference Intelligence Automation Level — **3.8 / 5**

### What is strong

- 14 upstream sources tracked.
- `references/index.json` exists with source metadata and feature mapping.
- Upstream adoption policy is a differentiator.
- Attribution/NOTICE/health report workflows are stronger than most AI coding framework repos.
- `references:report`, `references:health`, `references:index` scripts exist.

### Gaps

1. **Automation is mostly reporting, not change detection**
   - Good local reports, but no scheduled upstream diff watcher apparent.

2. **No explicit "adapted vs inspired vs rejected" machine-readable maturity tracking per feature**
   - Policy exists, but feature-level status could be stronger.

3. **No automated license-risk score per source**
   - Some classification exists; could be formalized.

4. **No backlink trace from local skill/command/template to source feature**
   - Traceability exists broadly, but source-to-local mapping could become more enforceable.

### Improvements

- Add `reference-feature-map.schema.json`.
- Add source status lifecycle:
  - `candidate`, `audited`, `adapted`, `rejected`, `watching`, `deprecated`.
- Add `references:diff` that compares current upstream metadata to last known snapshot.
- Add CI/scheduled optional workflow for reference health (non-blocking).
- Add source-to-local traceability report.

## 8. CI/CD Pipeline Maturity — **4.0 / 5**

### What is strong

- 13/13 validation gates pass.
- CLI smoke and adapter smoke tests exist and are included.
- Validation includes repo, references, schemas, traceability, injection, secrets, memory redaction, E2E, dashboard sync, evaluation report.
- GitHub Actions exist for validation/smoke.
- Release automation exists (`scripts/release.mjs`, bump script, release checklist).

### Gaps

1. **CI does not catch release metadata drift**
   - README v0.4.0 claim passed v1.0 validation.

2. **Schema validation is weak**
   - JSON Schema files are checked for shape, but not deeply used to validate instances.

3. **Runtime conformance is not tested**
   - No test that initializes runtime, creates each item type, validates schemas, corrupts state, and expects failure.

4. **Adapter smoke lacks execution**
   - No temp-dir CLI init or snippet execution.

5. **No link checker**
   - Internal doc links outside traceability scope can drift.

### Improvements

- Add CI gates:
  - `validate:release-metadata`
  - `validate:markdown-links`
  - `smoke-test:runtime`
  - `smoke-test:mcp`
  - expanded `smoke-test:cli`
- Add generated dashboard validation that consumes shared test metadata.
- Add `release:verify-tag` for local release flow.
