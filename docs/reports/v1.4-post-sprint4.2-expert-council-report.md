## Blockers before next feature sprint

### B1 — `vibe doctor --json` does not output valid JSON

Manual check:

```bash
node scripts/vibe-cli.mjs doctor --json
```

Output starts with human text:

```text
Vibe Coding OS — Health Check

✓ package.json
✓ node_modules
...
```

This makes stdout invalid for `JSON.parse` even though the flag promises JSON mode.

**Impact:** automation cannot consume `doctor --json`; smoke tests missed this because they only assert exit code.

**Fix:** in JSON mode, emit only `JSON.stringify(report, null, 2)` and suppress all banners/check output. Add CLI contract tests that parse stdout.

### B2 — Event Store v2 sequence assignment is race-prone

`appendEventV2()` currently:

1. loads `events-metadata.json`
2. assigns `seq = meta.nextSeq`
3. appends JSONL
4. writes metadata

There is no lock around this critical section.

**Impact:** concurrent appends can produce duplicate sequence numbers, lost metadata increments, or incorrect `lastEventId`.

**Fix:** lock event append operations with `withLock(store, 'events', ...)`, reconcile metadata from log before assigning seq, then append and persist metadata inside the lock.

### B3 — Event append + metadata update is not transactional

A crash between appending `events.jsonl` and saving `events-metadata.json` leaves divergent state. `getEventMetadata()` partially masks this with inferred totals, but the next append still trusts stale metadata.

**Impact:** metadata drift can become permanent and sequence assignment can remain wrong.

**Fix:** treat JSONL as source of truth; metadata is cache. Reconcile before append and expose metadata consistency in doctor.

### B4 — Idempotency is advertised but non-functional

`appendEventV2(..., { idempotent: true })` generates a new event ID internally, then checks whether that new ID already exists. This can only match on random ID collision.

**Impact:** false sense of deduplication safety.

**Fix:** support `options.idempotencyKey` and persist/query it. Calling append twice with the same key should return the same event and not increment sequence.

### B5 — Event Store v2 is not canonical yet

`task-store.mjs` still writes task events through legacy `events.mjs::appendEvent()`, while new CLI/doctor surfaces use Event Store v2.

**Impact:** two event APIs write the same file with different fields and guarantees. Most task events do not have `seq`, `correlationId`, or `causationId`.

**Fix:** either wrap legacy `appendEvent()` around v2, or document v1/v2 split explicitly. Preferred: make v2 canonical while keeping old function as compatibility wrapper.

## Warnings to address in Sprint 4.3

### W1 — `vibe events` shows oldest events while labeling them recent

`cmdEvents()` calls `listEventsV2({ limit })`, which returns the first N events, then labels them “Recent events.”

**Fix:** add tail/latest behavior or read all and slice the last N for current small-log assumption.

### W2 — CLI JSON mode lacks contract tests

Smoke tests assert exit status only. They did not catch invalid `doctor --json` output.

**Fix:** add tests that spawn CLI commands and `JSON.parse(stdout)`:

- `doctor --json`
- `doctor --project <tmp> --json`
- `events --json`

### W3 — `eventStream()` is not actually streaming

Implementation reads the whole file with `readFile()`, while comments claim batch/memory-efficient streaming.

**Fix:** either implement line streaming via `readline/createReadStream`, or update comments to say it is an async iterator over loaded file content.

### W4 — Doctor health semantics are too loose

`healthy` is true when `errorCount === 0`, even with warnings. Formatted output can show `HEALTHY` despite corruption warnings.

**Fix:** expose both:

- `operational`: no errors
- `clean`: no errors and no warnings
- `hasWarnings`: warning count > 0

Then format summary accordingly.

### W5 — Config parse errors may be misclassified

`loadConfig()` returns defaults with `_error` instead of throwing. Doctor expects thrown errors and may not warn properly on malformed config.

**Fix:** doctor should inspect `config._error`, or `loadConfig(store, { strict: true })` should throw.

### W6 — Config policy is mostly advisory

Config defines values like `maxTaskLease`, `heartbeatInterval`, `eventRetentionDays`, and `maxItemsPerStore`, but task APIs do not consistently enforce them.

**Fix:** enforce lease caps in `claimTask()`, `heartbeatTask()`, and `renewTaskLease()`; add tests.

### W7 — Existing CLI bug: undefined `warn`

Reviewer found `cmdInstallPack()` uses `${warn}` but constants define `ok`, `fail`, and `info`, not `warn`.

**Fix:** define `warn` constant or use `c.yellow` directly. Add a regression smoke test for overwrite-protection failure path output.

### W8 — Runtime local state/schema mismatch surfaced in `runtime:validate`

Architect attempted `npm run runtime:validate --silent` and saw failures around `claim: null` and history `from/to: null` being rejected by schemas.

**Assessment:** likely local ignored runtime data/schema mismatch, but important because code creates `claim: null` and history entries with null transitions.

**Fix:** inspect schemas and generated runtime objects; allow null where intentionally produced, or stop writing null.

## Product positioning review

The runtime work is still aligned **if it remains optional and local**:

> Vibe Coding OS is a portable workflow contract + discipline layer for AI coding across tools.

The risk is scope creep: multi-workflow orchestration, event replay, approvals, and policy can start resembling a runtime engine. Avoid competing with CrewAI/LangGraph/OpenHands. The product advantage should remain:

- `vibe init --profile X --tools Y`
- `vibe export all`
- portable instructions/rules/templates/skills
- optional local guardrails for discipline, audit, and recovery

Therefore Sprint 4.3 should strengthen runtime correctness and explain the boundary, not add a new orchestration engine.
