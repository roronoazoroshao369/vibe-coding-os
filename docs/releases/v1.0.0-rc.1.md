# Vibe Coding OS v1.0.0-rc.1 — Prerelease Notes

> **Status:** Release Candidate 1 — not final. Use this RC to validate the v1.0 stable workflow framework before the final v1.0.0 release.
> **Tag:** `v1.0.0-rc.1`

---

## RC Scope

v1.0.0-rc.1 is the first release candidate for the **v1.0 Trusted Workflow Framework**. This RC freezes the stable core workflow contract, formalizes validation and release gates, documents adapter support tiers, and establishes a release-candidate feedback cycle — all without expanding the feature surface beyond release readiness, validation, compatibility, and documentation clarity.

### In Scope

- Frozen and documented core workflow contract (Intent → Spec → Plan → Implement → Test → Review → Memory → Merge)
- Stable registry schema contracts for skills, commands, templates, and reference intelligence
- Objective release gates: 13/13 validation checks (repo structure, references, traceability, injection, secrets, memory redaction, adapter smoke, CLI smoke, E2E, schema validation, dashboard sync, evaluation report)
- RC handling process for feedback triage (blocker → important → follow-up) before final v1.0.0
- Documented adapter support tiers (Tier 1 Full: Claude Code, Codex CLI; Tier 2 Community: Cursor, Gemini CLI)
- Compatibility & support policy, support matrix, contribution governance, and release automation

### Out of Scope

- New workflow phases, mandatory artifacts, or broad command/skill expansion
- Runtime feature expansion beyond current optional runtime (`runtime/`)
- Tool-specific behavior guarantees beyond documented support tiers
- Breaking changes to published skills, commands, adapters, or workflow semantics

## What Is Stable in v1.0

The following are considered stable and frozen for the v1.0 release series:

- **Core workflow contract** — 8-phase pipeline (Intent → Spec → Plan → Implement → Test → Review → Memory → Merge) with adaptive task tiers (Tiny, Small, Medium, Large, Risky)
- **Registry schemas** — JSON validation contracts for skills, commands, templates, and reference index
- **Validation gate** — 13 automated checks as the release-blocking gate; all must pass before any v1.0+ release
- **Adapter support tiers** — Tier 1 (Full): Claude Code, Codex CLI; Tier 2 (Community): Cursor, Gemini CLI
- **Compatibility & support policy** — Semantic Versioning, breaking change definitions, deprecation process, release gate requirements
- **Skill packs** — Core Solo Developer, Memory-Safe, Multi-Agent, Upstream Intelligence
- **CLI helper commands** — `vibe init`, `vibe doctor`, `vibe stats`, `vibe list-skills`, `vibe list-commands`
- **Documentation** — Bilingual (English + Vietnamese), quickstart guides, tutorials, release-packaging guide

## How to Upgrade from v0.4.0

Upgrading from v0.4.0 to v1.0.0-rc.1 does **not** require workflow changes for most users. The core markdown-first usage model is unchanged.

1. **Clone or pull the RC tag:**
   ```bash
   git fetch origin
   git checkout v1.0.0-rc.1
   ```

2. **Re-run validation** to confirm your local environment passes all gates:
   ```bash
   npm run validate:all
   ```

3. **Regenerate the dashboard** to reflect the actual RC state:
   ```bash
   npm run dashboard:generate
   ```

4. **Adapter users:** Check `docs/support-matrix.md` for your tool's tier and follow `docs/QUICKSTART.md` for setup. Claude Code and Codex CLI remain Tier 1 (Full). Cursor and Gemini CLI remain Tier 2 (Community).

5. **If you use the optional runtime:** Re-run the installer (`node runtime-install.mjs`) — the runtime is not release-blocking and may have independent updates.

## What to Test

Focus RC feedback on these areas. Report any issues using the process below.

### Priority Test Areas

1. **Validation gates** — Run `npm run validate:all` and confirm 13/13 gates pass on your environment (OS, Node version, Git setup).
2. **Adapter install workflows** — Follow `docs/QUICKSTART.md` for your adapter (Claude Code, Codex CLI, Cursor, Gemini CLI). Do the instructions work end-to-end?
3. **CLI commands** — Run `vibe doctor`, `vibe stats`, `vibe list-skills`, `vibe list-commands`, `vibe init`. Do they produce expected output without errors?
4. **End-to-end workflow test** — `npm run test:e2e` should pass with all assertions succeeding.
5. **Dashboard accuracy** — Run `npm run dashboard:data` and `npm run dashboard:generate`. Does the output match your local repo state?
6. **Documentation clarity** — Review `docs/QUICKSTART.md`, `docs/TUTORIAL.md`, `docs/support-matrix.md`. Are instructions clear enough for a new user?
7. **Memory redaction** — Run `node scripts/verify-memory-redaction.mjs` and confirm 30/30 tests pass.
8. **Secret scanning** — Run `node scripts/validate-secrets.mjs` and confirm 0 secrets found.
9. **Upgrade path** — If you have a v0.4.0 deployment, test the upgrade steps above and report any friction.

### What We're NOT Looking For

- Feature requests or scope expansion for v1.0 (those go to the post-v1.0 roadmap)
- Runtime tool-specific bugs outside the core layer
- Cosmetic doc improvements (welcome but not release-blocking)

## How to Give Feedback

Feedback is critical to making v1.0 final. Use one of the following methods:

1. **GitHub Issues** — Use the issue templates:
   - Release checklist — for RC validation observations
   - Compatibility report — for adapter-specific issues
   - Safety / eval report — for validation or safety regressions
   - General bug report — for other issues

2. **Feedback classification** — Issues will be triaged as:
   - **Blocker** — must fix before v1.0.0 final
   - **Important** — fix before final if low risk; otherwise documented deferral
   - **Follow-up** — tracked for post-v1.0 work

3. **RC feedback window** — Opens at v1.0.0-rc.1 publication and closes when release manager approves final v1.0.0. All blocker issues must be resolved before final release.

4. **What to include** — Always paste the output of `npm run validate:all` (or the specific failing gate), your adapter and OS/Node versions, and steps to reproduce.
