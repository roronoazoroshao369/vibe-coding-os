# v1.0 Release Plan

v1.0 is the stability and release milestone for Vibe Coding OS. It promotes the existing markdown-first workflow framework to a trusted, supportable release without expanding the feature surface beyond release readiness, validation, compatibility, and documentation clarity.

## Scope Definition

### In Scope

- Freeze and document the stable core workflow contract: Intent → Spec → Plan → Implement → Test → Review → Memory → Merge.
- Confirm registry schema stability for skills, commands, templates, and references.
- Publish objective release gates for validation, safety, adapter compatibility, documentation, and changelog hygiene.
- Establish release-candidate handling for `v1.0.0-rc.1` before final `v1.0.0`.
- Document adapter support expectations and optional runtime boundaries.
- Produce release notes, readiness evidence, and post-merge verification steps.

### Out of Scope

- New workflow phases, new mandatory artifacts, or broad command/skill expansion.
- Runtime feature expansion beyond current optional runtime support.
- Tool-specific behavior guarantees beyond documented adapter support tiers.
- Breaking changes to published skills, commands, adapters, or workflow semantics unless explicitly approved and documented.

## v1.0 Done Criteria

v1.0 is done when all criteria below are met:

1. Core contract, support policy, release plan, RC checklist, and support matrix exist and are internally consistent.
2. `docs/ROADMAP-STATUS.md` and `docs/DASHBOARD.md` reflect current release status.
3. `CHANGELOG.md` contains the final v1.0 release notes before tagging.
4. All required validation gates pass locally and in CI where applicable.
5. Tier 1 adapters pass smoke tests and documentation checks.
6. No broken internal references, unreviewed orphan warnings, realistic secrets, or unresolved release blockers remain.
7. RC feedback has been triaged, fixed or deferred, and documented.
8. Final release tag and GitHub Release are created only after the release manager signs off.

## Required Gates and Commands

Run these commands from the repository root unless noted otherwise.

### Required for Every v1.0 RC and Final Release

```bash
npm run validate
npm run validate:all
npm run eval:report
npm run smoke-test:cli
npm run test:e2e
node scripts/smoke-test-adapters.mjs
node scripts/validate-secrets.mjs
npm run dashboard:data
```

### Required When Relevant Files Change

```bash
npm run validate:schemas        # schema or registry contract changes
npm run validate:references     # reference intelligence layer changes
npm run validate:traceability   # docs, commands, skills, templates, or links change
npm run dashboard:generate      # dashboard data or published status changes
```

### Release Blocking Conditions

- Any required command exits non-zero.
- Tier 1 adapter smoke tests fail.
- The changelog, release notes, dashboard, or roadmap contradict each other.
- A breaking change lacks migration notes or approval.
- Secret scanning flags realistic credentials in changed files.
- RC feedback contains unresolved release-blocking issues.

## RC Strategy

### 1. Prepare `v1.0.0-rc.1`

- Branch from the approved release-preparation branch.
- Confirm the workspace contains only intentional release changes.
- Update release notes and changelog with RC-specific highlights and known issues.
- Run all required gates and capture evidence.
- Tag only after release-manager approval:

```bash
git tag v1.0.0-rc.1
git push origin v1.0.0-rc.1
```

### 2. Feedback Window

- Collect feedback from adapter smoke users, maintainers, and documentation reviewers.
- Classify each issue as:
  - **Blocker:** must fix before final.
  - **Important:** fix before final if low risk; otherwise document deferral.
  - **Follow-up:** track for post-v1.0 work.
- Keep v1.0 focused on stability; do not add feature expansion during RC unless it fixes a release blocker.

### 3. Final `v1.0.0`

- Apply blocker fixes.
- Re-run the full required gate set.
- Regenerate dashboard if status data changed.
- Move changelog entries from `[Unreleased]` into `[1.0.0] — YYYY-MM-DD`.
- Create final tag only from the approved merge commit:

```bash
git tag v1.0.0
git push origin v1.0.0
```

## Release Manager Workflow

1. **Plan:** Confirm scope against this document and `docs/v1.0-rc-checklist.md`.
2. **Stabilize:** Reject unrelated feature expansion; accept only release-readiness, docs, validation, compatibility, and blocker fixes.
3. **Validate:** Run required commands and collect output snippets or CI links.
4. **Review:** Check release notes, changelog, roadmap, dashboard, support matrix, and adapter docs for consistency.
5. **Approve RC:** Cut `v1.0.0-rc.1` after gates pass and no blockers are known.
6. **Triage Feedback:** Record RC findings, resolve blockers, and explicitly defer non-blockers.
7. **Approve Final:** Re-run gates, verify post-merge state, tag `v1.0.0`, and publish GitHub Release.
8. **Verify Post-Release:** Confirm tag visibility, release page contents, install/onboarding docs, and clean dashboard/roadmap status.
